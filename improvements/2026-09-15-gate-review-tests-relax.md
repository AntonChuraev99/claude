# Гейт lite по умолчанию, одно ревью на дифф, тесты без мутации

## Цель

Пользователь: «не нравится скорость; результат при ослаблении ревью и тестов будет не сильно хуже, проще вернуться и поправить один баг за 30 минут, чем ждать эти проверки в каждой сессии». Задача — замерить по этапам, где время, и ослабить именно то, что ест его.

## Гипотеза

1. Один дифф ревьюится дважды разными правилами (CLAUDE.md «перед готово» + гейт 2.3b); оставить только 2.3b — он фоновый и инкрементальный — минус ~4 ч ожидания и 50 холодных контекстов в неделю без потери покрытия.
2. `lite` не существовал на практике из-за триггера «перед мержем» (та же эрозия, что delegation-rule-erosion). Дефолт `lite` с бухгалтерией только в `full` снимает ~половину из 6.9 ч генерации главного в гейте.
3. Мутация на каждом тесте оправдана для core-логики, но применялась и к обвязке; «тест только на чистую логику, зелёный = доказательство, мутация по запросу» снимает заметную часть из 11 ч прогонов. Красное репро багфикса не трогаем — дёшево и ловит регресс.

Ожидаемый суммарный выигрыш — 8–10 ч из 94 (приблизительно) критического пути; главный рычаг — генерация главного и ожидание специалистов, две верхние строки таблицы Baseline (источник: session-stages.py) — этой записью не закрывается.

## Изменения

- `CLAUDE.md`: «Роль главного агента» — пункт «Перед «готово» — diff ревьюит свежий субагент» заменён на «Ревью диффа — одно на задачу, в `/task-gate` 2.3b» (прецедент single-review-per-diff); «Тесты» — заголовок и первый пункт переписаны: тест только на чистую логику, зелёный прогон — доказательство, мутация по запросу (прецедент tests-logic-only-no-mutation-default); список `@test-expert` — «mutation matrix по запросу»; «Definition of Done» — `lite` дефолт, состав режимов, триггер «перед мержем» снят (прецедент task-gate-lite-default).
- `skills/task-gate/SKILL.md`: description; Re-entrancy — поле `deferredChecks` state-файла `task-gate-state.json` упразднено, поле `reviewedSha` пишется в любом режиме (имена полей — источник: `skills/task-gate/SKILL.md` → «Re-entrancy»; сам state-файл живёт в scratchpad сессии) (не проверено — файл вне репозитория); 1.1 — критерии `full` без «последнего прогона», состав `lite` и что он пропускает (не переносит); 2.0 — `⏱`-снимки только в `full`, в `lite` тот же фан-аут одним ревьюером; 2.3b — единственное ревью на задачу, в любом режиме; 2.4 active hygiene, 2.6, 2.9 rollup/hook-setup, Step 3, Step 4, 5.2 `⏱`, 5.2.1 — только `full`; Step 6 — гард `deferredChecks` снят.
- `skills/task-gate/references/diff-review-flow.md`, `diff-review-axes.md`: режим не условие запуска, один агент в `lite`, граница отревьюенного двигается в любом режиме, «ось не вернулась» — warning, не блокер Step 6.
- `agents/{feature,core,compose,android-platform,kmp,wasmjs,react-ui,nextjs}-expert.md`: description и пункт «тест на свой код» — логика-only, до зелёного, мутация по запросу (правка одним Python-скриптом из scratchpad сессии; число файлов — по списку в этой же строке, источник: diff --stat).
- `agents/test-expert.md`: description, «Скоуп», «Два режима», «Метод» п. 5, поле `mutation_check` в `COVERAGE_RESULT` (имена — источник: `agents/test-expert.md` → «Что вернуть») (не проверено — markdown, не код), «Чем докажешь» — мутация по запросу, зелёный прогон как результат.
- `references/claude-md-precedents.md`: три новых прецедента.
- `scripts/session-stages.py`: скрипт замера этапов по JSONL сессий (источник цифр выше и инструмент replay). После ревью 2.3b: события режутся по окну `DAYS` по времени события, а не по mtime файла (первый прогон без этого дал 101 ч вместо 93.7 — старые сессии, возобновлённые внутри окна, входили целиком); пустое окно не роняет агрегат.

## Target

К 2026-09-29 по `scripts/session-stages.py 14`:
- ревью-агентов на гейт ≤ 1.2 (было 2.3), ожидание ревью на критическом пути ≤ 2.5 ч/нед (было 5.6);
- фаза task-gate median ≤ 8 мин, p75 ≤ 12 мин (было 14.1 / 20.5); доля `lite` — по полю `mode` в `task-gate-timings.jsonl` (в `lite` строка пишется с `null`-длительностями), ожидание ≥ 70% гейтов (приблизительно);
- доля прогонов тестов внутри специалистов ≤ 10% их wall (было 17%), упоминание мутации ≤ 20% специалистов (было 64%) — целевые пороги (приблизительно); baseline (источник: session-stages.py);
- контрольная метрика: число задач, вернувшихся с багом после мержа (по «вернуться и поправить» в промптах пользователя и red-репро на свежих коммитах) — если > 2 за две недели, ревью в `lite` не трогать дальше, тесты вернуть на core.
