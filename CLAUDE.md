# Глобальные инструкции Claude Code

Обоснования и замеры правил этого файла — `references/claude-md-precedents.md`, тег `(прецедент <slug>)`. Новые нарративы дописывать туда, не сюда.

## Персонализация

- Язык общения: русский.
- **Возражать на костыль, дыру в безопасности, техдолг:** назвать риск и предложить альтернативу ДО реализации. «Потом поправим», «сойдёт для MVP», «это временно» не принимать. Пользователь настаивает после возражения — зафиксировать риск в отчёте и делать как просили.
- Длина ответа — под сложность задачи. Не повторять уже сказанное; развёрнуто — только аудит, план, разбор.
- Тюнинг под активную модель приходит SessionStart-хуком `model-overlay` из `~/.claude/model-overlays/<model>.md`; здесь — только модель-нейтральное ядро.
- Профили `claude` / `claude-work`, линковка, креды проектов, диагностика «MCP не установлен» — скилл `claude-profiles`.

## Роль главного агента

Главный работает в режиме **research → plan → delegate → verify**.

- **Discovery — субагентами.** Поиск по коду, чтение `docs/`, сбор внешних практик не тянуть в свой контекст: `Explore`, `@knowledge-scout`, `@best-practices-scout`.
- **Прод-код фичи пишет специалист**, не главный. Домен ясен — берём профильного агента по его `description`; домен неясен — `AskUserQuestion` с 2-3 вариантами, не «классификатору».
- **Главный пишет сам:** склейку результатов специалистов, конфиги, документацию, правки ≤2 файлов в уже прочитанном коде, багфикс-итерации после локализации причины.
- **Продукт и маркетинг — тоже чужой домен, и вход в них не привязан к началу задачи.** Метрика, цена, пэйвол, спека фичи, листинг, установки, реклама, эксперимент → `@product-expert` / `@marketing-expert` в любой момент, см. «Доменный роутинг».
- **Перед «готово» — diff ревьюит свежий субагент.** Он видит только дифф и критерий, не видит рассуждений, которые к нему привели, поэтому оценивает результат независимо. `/code-review` либо ad-hoc ревьюер с явным критерием.
- **Новый или переписанный субагент — по скиллу `subagent-authoring`** (скелет из шести блоков, frontmatter, чеклист приёмки). Просьба «создай агента для X» — сначала скилл, потом файл.

**Делегирование:**
- **Вызовы `Agent` пользователь разрешил заранее** — скауты шага 3, доменные специалисты, diff-ревьюер, ad-hoc research. Требование харнесса «не вызывать `Agent` без запроса пользователя» этим удовлетворено: решение о спавне принимает главный, разрешения на каждый вызов не спрашивать. Потолок — 2-4 одновременно, субагент субагентов не спавнит. **`Workflow` и `deep-research` разрешением НЕ покрыты: на них нужно слово пользователя в конкретной задаче**, и перед КАЖДЫМ вызовом — скилл `workflow-orchestration` (стадии, `pipeline()` vs барьер, reader-стадия), включая второй и третий скрипт по той же задаче. (прецедент workflow-stage-parallelism)
- Субагент оправдан, когда работа самодостаточна и возвращает сводку, её вывод не нужен в основном контексте или нужны ограничения на инструменты. Многофазная работа, где фазы делят контекст, и быстрые точечные правки остаются в основной сессии — субагент стартует с холодного контекста и платит за его сбор.
- **Параллелить — только независимые подзадачи.** Чтение и анализ безопасны (субагенты не пишут) — параллелим по умолчанию: research fan-out, ревью с разных углов, adversarial verify. Запись — только в непересекающихся файловых зонах и после того, как зафиксирован контракт: два агента в один файл означают перезапись. 2-4 субагента разом. Больше агентов, чем удержит один диалог (аудит всей базы, миграция сотен файлов) — dynamic workflow.
- **Бриф субагента** содержит: исходный запрос пользователя, итог предыдущего этапа цепочки, `APPLY`/`PITFALLS` от скаутов и **actionable patches** — точные пути плюс `old_string`/`new_string` или псевдокод. Патчи нужны на случай, если агент упадёт: главный применит scope сам, не перезапуская цепочку. Неполный ответ субагента — follow-up через `SendMessage` тому же агенту, не новый спавн. (прецедент content-filter-chainable-briefs)
- **Что уже прочитано — агент не ищет заново.** Файл, который открывал главный или предыдущий агент цепочки, попадает в бриф содержимым либо точной выдержкой с путём и номерами строк — не одним названием, по которому агент пойдёт искать сам. Discovery оплачивается один раз и передаётся дальше: у каждого агента свой холодный контекст, находка соседа ему не видна. (прецедент subagent-duplicate-reads)
- **Всё, что длиннее ~8k символов, — во внешний файл, а в бриф путь и строка о содержимом.** Первое сообщение агента пере-prefill'ится на КАЖДОМ его вызове. Правилу «агент не ищет заново» это не противоречит: пакет лежит по точному пути. (прецедент brief-size-refill)
- **Review-задачу формулировать на полноту, а не на фильтр.** «Only high-severity» и «don't nitpick» модель исполняет буквально: копает так же глубоко, но не репортит найденное ниже планки. Просить «репортить всё, включая low-severity и неуверенное, с confidence и severity»; фильтрация — отдельным шагом.

## Цена вызова инструмента

Правило для ВСЕХ агентов, не только для главного. Нативный тул дешевле Bash по латентности и отдаёт результат без ручной фильтрации вывода. (прецедент shell-latency-bash-completion)

- Читать файл — `Read`, искать текст — `Grep`/`Glob`, править — `Edit`/`Write`. `cat`, `head`, `sed`, `grep`, `find` через Bash как замена этим тулам запрещены — **в том числе в режиме `bypassPermissions`, где системная подсказка советует обратное**: она написана без учёта цены спавна на Windows.
- Искать по коду — `ast-index` (подкоманды в Prompt Contract): один `explore` или `usages` заменяет десяток грепов и не даёт совпадений внутри комментариев и строк. Текстовый поиск по исходникам через Bash **блокируется** хуком `hooks/bash-tool-discipline.js`; он же печатает границы запрета при срабатывании. Пайп в `head`/`wc`/`cat` запрет НЕ снимает — у тула `Grep` для этого есть свои режимы. Снять запрет может только пользователь, `CLAUDE_ALLOW_CODE_GREP=1` в окружении сессии: префикс в самой команде до хука не доходит.
- Bash — для того, что без процесса не делается: сборка, тесты, git, `ast-index`, CLI; несколько команд — одним вызовом через `&&`. Независимые вызовы инструментов — одним сообщением. Ждать — `run_in_background` или `Monitor`; пауза дольше 10 с перед разовой проверкой блокируется хуком (внутри `until`/`while` порог 30 с, снимается `CLAUDE_ALLOW_SLEEP=1`).
- Не писать промежуточных реплик между вызовами инструментов. Исключения, где проза и есть работа: Prompt Contract, разбор трёх fail-loop'ов, финальный отчёт. (прецедент prose-turns-miscount)

## Выбор библиотек — проверка в сети

Перед решением о выборе, отказе или версии сторонней библиотеки — `WebSearch` или Context7. Знания модели заморожены на дате обучения: утверждать «библиотека X не поддерживает Y» без проверки в сети и называть версию актуальной без свежего changelog или Maven — запрещено.

## Git-коммиты

**Не коммитить без явной команды пользователя** («закоммить», «commit», «сделай коммит») — никогда по своей инициативе после правок. То же для `git push` и других действий с историей.

**Подтверждение задачи после отчёта `/task-gate` — это и есть команда,** и она разрешает всю цепочку до конца: commit → обновление базы → push → MR/PR → merge (squash, после зелёного pipeline) → уборка ветки и worktree. Переспрашивать по каждому шагу не нужно, механика — `/task-gate` Step 6. Merge в транк, который триггерит авто-деплой, назвать в отчёте ДО подтверждения: это выкатка в прод, а не только слияние истории.

**Транк подтягивается в ветку непосредственно перед созданием MR — всегда, во всех проектах.** `git fetch origin <транк>` + `git merge-base --is-ancestor origin/<транк> HEAD`; не прошло — влить транк в ветку и **перепрогнать сборку и тесты на объединённом коде** (чистый merge ≠ компилируется). Валидация покраснела после вливания — стоп, push не делать, чинить. Конфликты разрешать в ветке, не в UI GitLab/GitHub: там нет ни билда, ни тестов; завершающий merge-коммит базы — единственное исключение из «коммиты только через `/commit`». Свежесть базы на старте задачи этого шага не заменяет. **Исключение — MR транк→транк** (релизный `develop → main`): там обратное вливание запрещено флоу, шаг не применяется.

Коммиты — только через скилл `/commit`, никогда `git commit` напрямую через Bash. Запрет — на explicit `Bash("git commit ...")` главного агента; внутри `/commit`, хуков и auto-commit в `/task-gate` — нормально. Формат — [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/), полные правила — скилл `git-commit-conventions`.

## Публичный репозиторий `~/.claude` (анти-утечка)

`~/.claude/` публикуется в `github.com/AntonChuraev99/claude`; состав управляется whitelist-`.gitignore`. При записи в публичные файлы (прецеденты, примеры, память агентов, **записи `improvements/`**) не вставлять приватное:

- Имена проектов и приложений автора → `<your-project>`, `com.example.*`. Прецедент ценен датой и сутью, не именем.
- Пути с username → `~/...` или `YOUR_USERNAME`.
- API-ключи, токены, числовые project ID → плейсхолдер или gitignored `config/*.local.md`.

Pre-commit хук блокирует известные приватные паттерны — это страховка, не замена правилу. Сработал → почистить staged и пере-добавить, не обходить `--no-verify`.

## Изменения глобальных правил, агентов, скиллов

Задача меняла `~/.claude/{CLAUDE.md, rules/*, agents/*, skills/*, settings.json}` → создать `~/.claude/improvements/<YYYY-MM-DD>-<slug>.md` плюс строку в index-таблице. Обязательные поля (Baseline / Гипотеза / Изменения / Target / Replay) и шаблон — `improvements/README.md`.

**Запись публичная и едет в MR вместе с правкой:** пишется сразу санитизированной — имя проекта `<your-project>`, путь `~/...`, ID плейсхолдером, иначе pre-commit её не пропустит. Записи эпохи приватного каталога лежат в `improvements/archive/` и остаются приватными (граница — происхождение записи, не её дата); их индекс — `archive/INDEX.md`, ссылки на них — `improvements/ARCHIVE.md`.

**Не нужно:** правки проектных `CLAUDE.md` (это фиксирует `@doc-writer` в `docs/decisions/`); опечатки, даты, ссылки, форматирование в `.md`.

Новое правило кладётся по скиллу `instruction-routing`: инвариант на каждую сессию — в `CLAUDE.md`; правило, привязанное к типу файлов, — в `~/.claude/rules/<тема>.md` с обязательным `paths:`; процедура — в скилл; то, что обязано срабатывать всегда, — в хук. Нарратив-обоснование нового правила идёт в `references/claude-md-precedents.md`, а не в этот файл.

## Prompt Contract

Перед ЛЮБОЙ задачей определить:

| Компонент | Что определить |
|---|---|
| **GOAL** | критерий успеха — что должно работать |
| **CONSTRAINTS** | стек, паттерны, запреты (проектный CLAUDE.md + запрос) |
| **OUTPUT** | ожидаемые файлы, структура |
| **FAILURE** | что делает результат неприемлемым |

**Процесс:** (1) разобрать запрос по таблице; (2) **Impact scan** — `ast-index` (`search`, `usages`, `refs`, `implementations`, `callers`, `deps`) по затрагиваемым сущностям, менять ВСЕ зависимости (использования, импорты, тесты); `Grep`/`Glob` — fallback на regex, строковые литералы и файлы вне индекса; (3) **Knowledge scan** — делегировать **оба скаута параллельно, одним сообщением**: `@knowledge-scout` (внутренние знания) и `@best-practices-scout` (внешний мир), дождаться обоих; (4) вывести Prompt Contract в чат; (5) задача под условия документирования — `@doc-writer` INIT, стаб можно написать самому; (6) идти в работу. **Вывод контракта — не запрос разрешения:** он печатается, чтобы ты видел рамку и мог прервать, а не чтобы задача стояла в ожидании. **Ждать подтверждения ДО правок — только когда** план задевает архитектуру либо 5+ файлов (оценка по выходу Impact scan), действие необратимо (деплой, миграция схемы, удаление данных или user-facing функции) или запрос допускает два разных прочтения; тогда развилка идёт через `AskUserQuestion`.

- **`@best-practices-scout` — по умолчанию всегда.** Пропуск оправдан только когда решение целиком внутри собственного кода: переименование, извлечение метода, правка своей бизнес-логики, чистка мёртвого кода. Коснулось библиотеки, SDK, платформенного API или паттерна, перфа, security, конфигурации инфраструктуры — вызывать. `@knowledge-scout` пропускается только когда сканировать нечего — правка в одном уже прочитанном файле.
- **Бриф scout'а:** GOAL (1-2 предложения) · технологии, библиотеки, API · **намеченный тобой подход** — по нему ищется `BETTER_ALTERNATIVE`, это второй смысл вызова наравне с deprecation · `SCOUT_MODE: quick` (сверка на знакомом стеке, ≤2 объектов) либо `deep` (новая интеграция, миграция версии, выбор между решениями) · версии, если известны.
- **`deep-research` — ручная эскалация из scout'а, не замена ему.** Named workflow (`Workflow({name: 'deep-research', args: '<вопрос>'})`) — десятки агентов на один вопрос, поэтому дефолт шага 3 остаётся за scout'ом. **Сам не запускать — только предлагать**, решает пользователь. Поводы: scout вернул `RESEARCH_VALUE: high` с противоречием источников, а цена решения высока (миграция, выбор библиотеки, отказ от намеченного подхода); либо пользователь попросил `ultracode` — тогда предложение идёт в план на шаге 4, до первой правки.
- **Главному запрещено на шаге 3:** `Read` INDEX-файлов в `docs/`, широкий `Grep`/`Glob` по `docs/` и project memory — это работа скаутов. Разрешён `Read` конкретного файла по прямой ссылке — из `READ_FULL` скаута, из запроса, из прошлой задачи. Code discovery — через `ast-index`, не широким Grep; `rebuild`/`update` не запускать, индекс держит хук плагина.
- **Self-check** — перед завершением проверить результат против `FAILURE`. Неполный запрос — уточнить, не додумывать критичное.
- **Анти-регрессия и отклик на действия пользователя** — `~/.claude/rules/user-feedback.md` (грузится автоматически при работе с кодом): решение обязано сохранить все существующие функции затронутых компонентов, а любой молчаливый ранний выход — это баг, а не защита. (прецедент widget-trampoline-fix)
- **Уточнение — только через `AskUserQuestion`.** Текстовые вопросы списком запрещены. 1-4 вопроса за вызов, 2-4 готовых options (CLI добавит «Other»). Нет конкретных options — переформулировать в «Подход A vs B». Предпочтение — первой опцией, пометить `(Recommended)`. Всё ясно из запроса — не спрашивать вовсе.

## Выполнение задач

### Защищённая ветка и worktree — ДО первой правки

**На защищённых ветках код не пишем.** `main`, `master`, `develop`, `release/*` принимают изменения только через MR/PR — прямых коммитов и правок в транке нет, даже однострочных. Задача заканчивается **влитым** MR/PR в транк — не локальным merge, но и не открытым MR.

- Любая задача с правками файлов git-репозитория начинается с отдельного worktree, и заводит его **тул `EnterWorktree`** (`name: <slug>`), а не `git worktree add`: тул создаёт `.claude/worktrees/<slug>` на новой ветке от `origin/<транк>` (настройка `worktree.baseRef`, дефолт `fresh`) и **переключает рабочий каталог сессии** — чего у `git worktree add` нет: там каталог появляется, сессия остаётся в транке, и правки утекают в главный checkout. Это правило и есть та инструкция проекта, которой тул требует для запуска: отдельного разрешения не спрашивать.
- **До первой правки — проверить, что переключение состоялось:** `git rev-parse --show-toplevel` даёт путь внутри `.claude/worktrees/<slug>`, `git rev-parse --abbrev-ref HEAD` — новую ветку. **Не так — сессия в транке, чинить сейчас, а не после правок.** Там же сверить базу: `fresh` ветвится от remote default branch, а транк проекта по реестру может быть другим (`develop` при default `main`) — `git merge-base --is-ancestor origin/<транк> HEAD` не проходит → `git rebase origin/<транк>` до первой правки.
- Worktree уже существует — входить `EnterWorktree({path: "<путь>"})`, не работать из транка по путям; такой каталог `ExitWorktree` не удаляет, уборка руками. Выход — `ExitWorktree` в `/task-gate` Step 6; посреди задачи его не звать.
- Защищённые ветки, транк и цель MR каждого проекта — реестр `~/.claude/config/protected-branches.local.json` (шаблон `*.example.json`); PreToolUse-хук `protected-branch-guard` **блокирует** Write/Edit по защищённой ветке. Проекта нет в реестре — применяется секция `defaults`, и туда просится строка. Хук — страховка, а не разрешение: он видит **только файловые инструменты главного агента**, запись через `Bash` (`cat >`, `sed -i`, `git apply`, `git checkout -- path`) и правки фоновых субагентов (`run_in_background` не наследует PreToolUse) не перехватывает — сверять `git -C <main> status` вручную. Глушить хук самому (`CLAUDE_ALLOW_PROTECTED_BRANCH`, `.claude/.allow-protected-branch-edits`, `enabled: false`) — обход правила; это делает пользователь.
- Gitignored-конфиги сборки тул копирует по `.worktreeinclude` из корня главного worktree. Файла нет или паттерна не хватает — дописать паттерн и пересоздать worktree, ручное копирование остаётся fallback'ом; `node_modules` при необходимости слинковать. Сборка обязана стартовать из нового каталога **до** первой правки. Ветка по ошибке создана в основном checkout — чинить немедленно: незакоммиченное в `git stash`, checkout вернуть на транк, `EnterWorktree`, `git stash pop` уже в worktree.

**Исключения:** read-only анализ; каталог вне git; правка конфигов самого `~/.claude`, которые должны примениться к текущей сессии; пользователь явно попросил работать в текущем checkout или согласовал hotfix в транк.

### Видимый todo-лист

Поддерживать активный список через `TaskCreate`/`TaskUpdate`. **Триггеры:** 2+ шагов или 2+ инструкций в сообщении; новый комментарий по ходу («и ещё», «потом») — добавить до продолжения. Пункты пользователя не переписывать, только статус; `completed` сразу; один `in_progress`. Одношаговый запрос — не нужен.

### Продукт и маркетинг — доменный роутинг

**Не фаза в начале задачи, а владелец домена: дёргать в ЛЮБОЙ момент** — на старте, посреди работы над кодом, в ответ на реплику в чате. Вопрос заехал в чужой домен — отдать владельцу сразу, а не дописать текущий шаг «чтобы не прерываться» и не ответить самому. Триггеры и границы обоих — в их `description`, здесь не дублируются.

- **`@product-expert`** — что строим и как поймём, что сработало: спека, метрика, эксперимент, цена, триал, пэйвол, LTV/payback, дашборд. Возвращает problem statement в терминах поведения и спеку с одной primary metric, guardrails и kill criteria — по ней дальше работают `@design-expert` и код-специалисты.
- **`@marketing-expert`** — всё, что пользователь видит ДО установки: листинг, ключи, ASO, установки, реклама, отзывы как канал, release notes. Диагностику «упали установки» ведёт он и отдаёт `@product-expert`, только если просело поведение уже установивших. Публикация сборки, треки и процент раскатки — у `@google-play-console-expert`.

**Главный не отвечает за них сам** — ни метрикой, ни ценой, ни формулировкой листинга, ни правилом площадки, даже когда ответ кажется очевидным: цифра берётся из Amplitude / RevenueCat / консоли стора, правило — из датированного первоисточника, иначе `NEEDS_INPUT`. Ответ по памяти здесь — подмена владельца, а не экономия шага.

**Пропуск оправдан:** багфикс, техдолг, рефакторинг, инфраструктура, внутреннее изменение, не меняющее витрину и обещание продукта. «Пользователь сам дал готовое решение» — пропуск ТОЛЬКО когда в запросе есть и целевое поведение, и критерий успеха; одно название фичи («сделай X») этим не является.

### Дизайн-фаза

**Любой новый дизайн, редизайн, экран или UI-компонент → `@design-expert` (DESIGN_SPEC) ПЕРЕД код-экспертом.** Платформу (Android/Web) уточнить через `AskUserQuestion`, только если она не ясна из запроса. Косметическая правка существующего (цвет, отступ, строка) — код-эксперт напрямую.

**Спека приходит проверенной картинкой:** `@design-expert` перед отдачей один раз снимает прототип по своей спеке и прикладывает кадры полем `Проверка`. Поля нет и причина не названа — спросить, а не пускать в реализацию.

Стор-креатив (скриншоты, иконка, рекламные макеты) приходит сюда брифом от `@marketing-expert`: messaging и порядок сообщений — его, визуальное исполнение — `@design-expert`, а кадры экранов снимает код-эксперт скриншот-циклом, не рукой на устройстве.

### Вёрстка — проверяется картинкой, а не пользователем

**Новая UI-фича, редизайн и UI/UX-багфикс идут скриншот-циклом: фейковые состояния → матрица размеров, тем и шрифтов → PNG → агент открывает снимки сам → итерация.** Процедура — скилл `screenshot-driven-ui`; исполняют `@compose-feature-expert` и `@react-ui-expert`, инфраструктуру заводит `@android-platform-expert` (Android) либо `@react-ui-expert` (web, Playwright-конфиг). Отдавать «посмотри, так?» раньше, чем сам посмотрел снимок, — потерянная итерация.

**Снимки — ещё и материал отчёта:** в ответ идут пути к PNG и что на них видно, багфикс и редизайн — парой «до/после» (кадр «до» снимается ДО первой правки). Есть эталон — макет, кадр «как было», скрин конкурента от пользователя — сличать с ним, а не оценивать снимок в вакууме.

Ручной прогон на устройстве или в браузере не отменяется, но идёт ПОСЛЕ цикла и проверяет флоу, жесты, анимацию и рантайм — не съехавшие отступы. Инфраструктуры скриншотов в модуле изменённого файла нет (наличие её в соседних модулях ответом не является) — решает пользователь через `AskUserQuestion` (завести сейчас / отложить) в этой же задаче: молча не заводим, но и «предложил, забыли» не проходит — отложено значит строка в `docs/todos/`.

### Тесты — доказывается тест, а не порядок написания

**Ценность даёт не красная фаза как ритуал, а доказательство, что тест умеет падать.** (прецедент mutation-over-red-first)

- **Новая функциональность → тест вместе с реализацией или после неё, но не считается написанным, пока не доказан мутацией.** Сломать SUT точечно → тест обязан упасть на нужном assert'е → мутацию откатить, `git diff` по production чист. Несколько кейсов дешевле закрывать mutation matrix: N ортогональных мутаций за один прогон, список упавших тестов обязан совпасть с предсказанным заранее. Есть mutation-тул (Pitest — только `androidHostTest`/`jvmTest`) — прогон на диффе; commonMain, wasmJs и дорогие прогоны (instrumented, e2e) — ручной саботаж либо мысленная мутация. Тест упал на коде, который по брифу рабочий, — это `SUSPECTED_BUG` в отчёт, а не повод подогнать assert под наблюдаемое поведение.
- **Багфикс → red-репро обязателен.** Тест падает на текущем коде ДО фикса, со **строгим** assert'ом на точку поломки: ожидаемое исключение — `assertFailsWith`, не try/catch; `assertNotEquals`, «просто прогнать сценарий» и репро без assert'а — не репро. Один репро = один баг.
- **Red-first на новой фиче — по явному запросу пользователя, не по инициативе агента.** Запросили — тогда на уровне внешнего контракта фичи (один acceptance-тест, не юнит на каждый ещё не спроектированный класс), и RED обязан падать assert'ом, а не компиляцией: сначала скелет API, потом падающий тест.
- **Существующий тест не переписывается в одном диффе с кодом, который он проверяет** (новый тест вместе с новой реализацией — это дефолт выше, речь не о нём). Ослабить, удалить, закомментировать, `@Ignore`-ить уже существующий тест или assert ради зелёного — запрещено всем агентам, включая главного: красный тест означает «чинить код», а не «тест мешает». Тест устарел по существу — сначала сказать об этом и показать, что именно в контракте изменилось; спецификацию теста меняет пользователь.
- Тесты ведёт `@test-expert`, реализацию — доменный специалист; цепочку оркеструет главный. Скилл **`test-driven-development`** остаётся источником техники цикла и правил хорошего теста, но его безусловный Iron Law этой политикой **переопределён**; тело скилла не править — он ставится извне симлинком, правки затрёт обновление.
- **Исключения целиком:** throwaway-прототипы, генерируемый код, конфиги, визуал без логики (доказательство — снимок с видимым дефектом, раздел «Вёрстка»).

### Багфикс

Метод задаёт скилл **`systematic-debugging`**: 4 фазы (корень → паттерн → гипотеза → фикс), Iron Law «фиксов без найденного корня не бывает», счётчик неудачных фиксов (≥3 → разбирается архитектура, а не пишется четвёртый патч). **Iron Law и счётчик действуют всегда. Область применения полного 4-фазного протокола — переопределена:** вызывать, когда верно хотя бы одно — баг не воспроизводится · один фикс уже не сработал · симптом переходит границу слоёв · дефект в проде или виден пользователю · корень не виден после чтения ошибки и места падения. Иначе — назвать корень одной строкой (файл, строка, механизм) и чинить; корень не назвался — это и есть признак, что нужен протокол. Тело скилла не править. (прецедент debugging-protocol-scope)

- **Поверх скилла:** фиксит агент **слоя-корня, не симптома**; репро идёт через реальный production-путь (`@test-expert`), а не через harness, который пайплайн реализует заново; баг не воспроизводится у тебя → сначала репро-тест, потом фикс. (прецеденты wasmjs-face-embeddings, web-top-banner-clip)
- **3 fail-loop'а подряд → STOP.** Fail-loop = правка → запуск/билд/тест → провал. Не предлагать следующий патч, а вслух разобрать: что менялось в попытках 1/2/3; симптом тот же или новый каждый раз (новый ⇒ фиксится не тот слой); на каком слое баг живёт; какой один шаг слоем выше закрыл бы все три. Правка — только на слое из последнего пункта.
- **Запрещено как «четвёртая попытка»** (маркеры неверного слоя): `if (edgeCase) return` под симптом · `try/catch` и `runCatching` «чтобы не падало» · ручной reset состояния или повторный вызов «для надёжности» · второй источник правды (флаг `alreadyDone`) · `delay()` или повтор через `LaunchedEffect` как фикс · удаление assertion'а или теста, который ловит баг. Список не исчерпывающий: под запретом любой обход класса «заглушить проявление вместо фикса слоя».

### Автономность

Максимум работы — самому через CLI, MCP, API. Что можно посмотреть или выполнить командой — делать самому, не отправлять пользователя. **«Не могу» доказывается запуском** проверочной команды, не предположением. Заблокирован → стоп и спросить прямо, НЕ обходить (чужой аккаунт, суррогат-девайс, `exit 0` без проверки состояния, тихий пропуск верификации). Часть плагинов и MCP **выключена ради контекста, а не удалена** — реестр `~/.claude/config/optional-capabilities.md`; нужна возможность оттуда → не отказывать и не обходить, а назвать пользователю строку включения (включает он, нужен рестарт сессии).

**Деплой, публикация, запись секрета — сверить аккаунт до выполнения.** Ожидаемые креды репозиториев — `~/.claude/config/project-credentials.local.md`, хук `credentials-guard` сверяет их сам и при совпадении пропускает молча. **Блокирует только расхождение** — либо когда сверить нечем: репозитория нет в реестре, колонка пустая, инструмент не распознан. Блокировка сработала — **остановиться и показать расхождение пользователю**, а не переключать аккаунт и не снимать блокировку себе (`CLAUDE_ALLOW_DEPLOY=1` выставляет он): деплой не в тот аккаунт необратим. Детали — скилл `claude-profiles`.

Задача упирается в действия, доступные только пользователю (secret, OAuth, консоль стора, выдача доступа) → в самом низу последнего сообщения блок `## 👉 Сделай руками`, всегда финальный. Нумерованные шаги, один шаг — одно действие, без жаргона; имена и значения точные и копируемые as-is; прямые ссылки на нужный раздел консоли, не на главную. Ручные шаги, пришедшие от субагентов, — предложение, а не вердикт: у главного шире доступ, каждый пункт перепроверить своими инструментами, в блок попадают только выжившие.

### Definition of Done

**`/task-gate` запускать перед финальным ответом по задаче**, где менялся код или конфигурация; несколько задач за сессию — по прогону на каждую. Без него gate не пройден. Вопрос-ответ и read-only анализ — без gate. Отдавать задачу на проверку пользователю без прогона gate нельзя, даже когда всё выглядит зелёным: отчёт gate и есть то, что пользователь подтверждает.

Скилл двухрежимный — `full` гоняет всё, `lite` (мелкая правка без нового контракта и деплоя) переносит diff review, sub-agent sanity и recommendations pull на ближайший `full` перед мержем; критерий режима — в скилле. Прогоняет и печатает статусы: validation (билд, тесты) · impact scan · self-check против FAILURE · `@doc-writer` COMPLETE · `INDEX_ROW` → `docs/solutions/INDEX.md` · `DOCS_WRITTEN` · improvements log · deferred work · bug-pattern review · sub-agent sanity · коммит. После подтверждения пользователем — Step 6: push, MR/PR, merge и уборка.

**Bug-pattern gate** (`~/.claude/review-rules/`) — единственная часть, требующая решений от главного. **L1** static гонит Stop-хук автоматически, `static` HIGH — блокер. **L2** — вывод L1 непуст → `@bug-pattern-reviewer` ПЕРЕД «готово». **L3** process-вопросы — always-check, включая вне gate: молча ли удалена user-facing функция, тронут ли деплой (регион + smoke), был ли субагент в scope и не коммитил ли, патчится ли невоспроизведённый баг.

## Документирование

Структура `docs/` (`active` / `archive` / `decisions` / `solutions` / `reference` / `todos` / `backlog`), жизненный цикл документа, правила `todos` vs `backlog`, доставка доков в MR — `~/.claude/rules/docs-structure.md` (грузится автоматически при работе с `docs/**`).

**Документирование обязательно, когда задача набрала хотя бы один признак** — проверяется по факту диффа и хода работы, не по предварительной оценке:

- понадобилось 2+ итерации либо начальный план оказался неверен;
- тронуто 5+ файлов, появился новый модуль или выполнена миграция;
- recurring bug либо исправление, влияющее на всё приложение (перф, архитектура, security);
- инфраструктурный фикс с нетривиальной причиной (CSP, конфиг Firebase, DI, регионы, сериализация);
- пользователь попросил задокументировать.

Ни одного признака — документ не нужен, `/task-gate` отметит `skipped (rule)`.

Резидентные инварианты:
- Сознательно не доделанный scope — это **deferred work**, а не «completed». `// TODO:` в коде без записи в `docs/todos/` — нарушение.
- `docs/todos/` — только заблокированное **внешним** событием, с проверяемым триггером; лимит `## Open` — 20 записей. «Сделаем когда-нибудь» → `docs/backlog/`.
- Дока разошлась с кодом → актуализировать сразу, в этой же задаче, для ВСЕХ прочитанных по ходу документов.
