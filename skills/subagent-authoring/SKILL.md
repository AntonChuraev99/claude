# Как писать субагента

Определение субагента — не эссе о специальности, а контракт: что агент видит, чего не трогает, что обязан вернуть и чем докажет, что работает.

## Frontmatter — официальные поля

```yaml
---
name: compose-feature-expert          # имя, по нему @-упоминание
description: <когда вызывать + DO NOT use>   # по нему Claude решает делегировать
tools: Read, Grep, Glob, Edit, Write, Bash   # allowlist; чем уже, тем лучше
model: opus                            # opus | sonnet | haiku | inherit
memory: user                           # user | project | local — своя база знаний агента
skills: material-3-skill, edge-to-edge # полностью препоадятся в контекст агента
color: green
---
```

- **`description` — самое важное поле.** По нему и только по нему модель решает, делегировать ли сюда. Пишем: когда вызывать (конкретные триггеры и формулировки задач) + **`DO NOT use for:`** с явным перечислением, куда уходят соседние случаи. Расплывчатое описание = агент срабатывает не на те задачи или не срабатывает вовсе.
- **`tools`** — только необходимое. Ревьюер без `Edit`/`Write` физически не сможет «заодно поправить».
- **`memory`** — включает агенту собственную базу знаний. Накопленный опыт живёт там, а не в теле промпта.
- **`skills`** — препоад: содержимое перечисленных скиллов целиком уезжает в контекст агента при запуске. Класть 1-2 действительно обязательных; остальное агент подтянет сам через Skill tool.

## Скелет тела — шесть блоков

```markdown
## Перспектива
<Чем этот агент смотрит на задачу и чего он принципиально не видит.
Не «Ты опытный senior-инженер с 10 годами опыта» — а какой угол зрения.>

## Скоуп
Делает: <2-5 пунктов конкретной работы>
Не делает: <что уходит соседям> → `@<агент>`
Задача упирается в чужой скоуп → `STATUS: NEEDS_DELEGATION <agent>`, не «по краю».

## Что должно прийти в брифе
<Без чего работа невозможна: контракт API, DESIGN_SPEC, пути, APPLY/PITFALLS.
Не пришло — вернуть `STATUS: NEEDS_INPUT`, а не додумывать.>

## Метод
<3-6 шагов, специфичных ИМЕННО для этого агента.
Общие правила из CLAUDE.md не пересказывать — субагент грузит их сам.>

## Что вернуть
<Жёсткие поля ответа: список изменённых файлов, риски, что проверить главному,
опционально actionable patches. Формат — не «подробный отчёт», а перечень полей.>

## Чем докажешь
<Проверка, дающая pass/fail: тест, компиляция, скриншот, команда с ожидаемым выводом.
Агент, который не может себя проверить, отдаёт непроверенную работу главному.>
```

## Чего в агенте быть не должно

| Не класть | Почему | Куда |
|---|---|---|
| Пересказ `CLAUDE.md` и правил | субагент грузит `CLAUDE.md` и `~/.claude/rules/` сам — это мёртвые токены | удалить |
| Прецеденты вида «баг 2026-04-28 в фиче X» | опыт прошлых задач раздувает промпт и стареет | `agent-memory/` (поле `memory:`) |
| — исключение | прецедент **одной строкой в скобках**, объясняющий, откуда взялся жёсткий запрет («cap ≤3 git-вызова», «не коммитить»), остаётся: без причины запрет читается как каприз и обходится | — |
| Структуры каталогов и паттерны конкретного проекта | user-level агент применяется во **всех** проектах | проектный `.claude/agents/` либо skill с `paths:` |
| Персона: «ты senior с большим опытом» | над-ограничение персоной слабее явной перспективы | блок «Перспектива» |
| Длинные листинги кода как иллюстрация | тело агента — не учебник | skill или `agent-memory/` |
| Общий протокол специалиста | дублируется в каждом агенте | `CLAUDE.md` — там роль главного и границы делегирования |

**Объём — 60-120 строк.** Больше 150 — почти наверняка внутри лежит что-то из таблицы выше, это блокер. Меньше 60 — проверь, все ли шесть блоков заполнены содержательно; сам по себе компактный агент дефектом не является. Замер по 15 переписанным определениям (2026-08-03) дал 60-87 строк при полном наборе блоков — нижняя граница не повод дописывать воду.

## Чеклист приёмки

1. `description` называет и триггеры, и границы. Фрагмент пишется английским литералом **`DO NOT use for:`** — по нему идёт проверка грепом; русское «DO NOT use для» её не проходит.
2. `tools` — минимальный набор; у ревьюеров и скаутов нет `Edit`/`Write`.
3. Тело укладывается в шесть блоков, посторонних разделов нет.
4. Нет ни одного упоминания конкретного проекта, если агент лежит в `~/.claude/agents/`.
5. Есть блок «Что вернуть» с перечисленными полями.
6. Есть блок «Чем докажешь» с проверкой, дающей pass/fail.
7. Границы взаимны: если A отправляет случай к B, у B в `description` этот случай упомянут — и B его действительно принимает, а не отводит обратно.
8. Адресат маршрутизации назван по имени (`@compose-feature-expert`), а не плейсхолдером («код-эксперты», `<code-expert>`): по плейсхолдеру взаимность не проверяется и делегирование не срабатывает.
9. Объём в пределах 60-120 строк.

## Проверка после правки

```bash
wc -l ~/.claude/agents/*.md          # объём
grep -c "DO NOT use" ~/.claude/agents/<name>.md   # description содержит границы
```

Плюс прогон на реальной задаче: сформулировать запрос, который **должен** попасть в этого агента, и запрос, который должен уйти соседу, — и посмотреть, куда уходит делегирование.
