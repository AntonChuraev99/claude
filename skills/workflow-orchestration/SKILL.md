# Оркестрация Workflow

`Workflow` запускается ТОЛЬКО по явному слову пользователя в конкретной задаче — предварительное разрешение на `Agent` его не покрывает. Этот скилл — про то, как написать скрипт, когда разрешение получено.

## Параллелится каждая стадия

**Включая spec и impl, и в КАЖДОМ вызове `Workflow`, а не только в первом.**

- Стадии соединять `pipeline()`. Элемент проходит все стадии независимо: item A может быть на стадии 3, пока item B ещё на первой. Wall-clock = самая длинная цепочка одного элемента, а не сумма самых длинных стадий.
- `parallel()` — барьер. Оправдан только там, где следующей стадии нужен весь результат предыдущей разом: дедуп находок между собой, ранний выход по нулю находок, сравнение находок друг с другом. Точная семантика обеих функций — из контракта тула `Workflow`, не из пересказа здесь.
- **Барьер НЕ оправдывают:** «стадии концептуально разные» и «сначала соберу, потом отфильтрую». Фильтрация и трансформация делаются внутри стадии `pipeline()`, а не между барьерами.
- Impl параллелится по непересекающимся файловым зонам, и зоны фиксирует spec-стадия — требовать от неё явный список зон отдельным полем `schema`. Два агента в один файл означают перезапись.
- Потолок «2-4 субагента разом» к зональному impl **не относится**: он про агентов, делящих один контекст задачи, а не про зональных исполнителей по готовой спеке. Их число задаётся числом зон.

Замер сессии 2026-08-18 на одном железе: review-стадия из 81 агента — ×7.3, 66 минут; impl-стадия из 12 агентов — ×1.5, 306 минут. Полный разбор — `references/claude-md-precedents.md`, прецедент `workflow-stage-parallelism`.

## Общий контекст собирает первая стадия

Скрипт не имеет доступа к ФС. Отсюда правило:

1. Файлы, нужные всему фан-ауту, читает **ОДИН reader-агент** первой стадией `pipeline()`.
2. Reader делает `Write` контекст-пакета в scratchpad-каталог сессии.
3. Reader возвращает через `schema` **ПУТЬ** к пакету, а не его содержимое.
4. Остальные агенты получают путь в `prompt` и читают пакет по нему.

**Запрещено:** пускать N агентов независимо грепать одно и то же; передавать содержимое пакета прямо в `prompt`. Ограничение «скрипт не умеет в ФС» снимается reader-агентом, а не обходится размером `prompt` — первое сообщение агента пере-prefill'ится на КАЖДОМ его вызове.

Требование относится к КАЖДОМУ вызову `Workflow` по задаче. Типичный сбой: reader-стадия стоит только в первом из четырёх скриптов, остальные три пускают зональных агентов читать самостоятельно. Прецеденты `subagent-duplicate-reads` и `brief-size-refill` там же.

## Приёмка скрипта

- Каждая стадия — `pipeline()`, кроме тех, где выписана причина барьера.
- Есть reader-стадия, и она возвращает путь, не содержимое.
- Ни один `prompt` не длиннее ~8k символов.
- Spec-стадия отдаёт явный список файловых зон, зоны не пересекаются.
- Если workflow ограничивает покрытие (top-N, отказ от повтора, сэмплирование) — это в `log()`, а не молча.
