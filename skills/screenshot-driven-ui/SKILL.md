# Screenshot-driven UI

Вёрстка проверяется на PNG, снятом на JVM за секунды, а не установкой на устройство. Ключевое: **картинки смотрит сам агент** через `Read` — цикл «правка → снимок → взгляд → правка» замыкается внутри одного вызова, без круга через пользователя.

## Когда

**Входы (цикл обязателен):** новый экран или UI-компонент · редизайн и реализация `DESIGN_SPEC` · UI/UX-багфикс, где симптом видно глазами (съехало, обрезалось, перекрыто, не влезло, не читается, ломается на планшете или при fontScale 1.5).

**Не применять:** поведение и навигация (клик ведёт не туда) · жесты, скролл, drag · анимация и переходы · рантайм-DI и краши · тайминги и гонки · перф. Скриншот такое не ловит — там обычный тест и реальный прогон.

**Не путать с соседями:** `/mcp-mobile-test` снимает живое устройство (после сборки и установки), `layout-debug` разбирает дерево работающего UI через adb. Здесь — JVM-снимки **до** запуска, без устройства.

**Кто что пишет:** превью и фейковые состояния лежат в main source set, то есть это прод-код — его пишет UI-специалист (`@compose-feature-expert` / `@react-ui-expert`). `@test-expert` работает с уже существующими превью и с тестовым sourceSet. `@design-expert` делает **один** прогон на выбрасываемом прототипе перед отдачей спеки (ниже), а не ведёт цикл.

**Разовый прогон дизайн-спеки.** Спека проверяется картинкой ровно один раз, до передачи код-эксперту: прототип по спеке (для web — готовый HTML в браузере, для Android — composable в тестовом sourceSet), кадры минимум четыре (самый узкий, самый широкий, тёмная тема, fontScale 1.5), найденное правится **в спеке**. Прототип выбрасывается: scratch-каталог или тестовый sourceSet, в прод-пути и в коммит не уезжает. Инфраструктуры нет — заводить её ради спеки не надо, пометить спеку непроверенной.

## Цикл

### 0. Инфраструктура

Проверить, есть ли она **в МОДУЛЕ правящегося файла**: `<module>/build.gradle.kts` + каталог `<module>/src/androidHostTest/roborazzi/`, наличие `@Preview` в модуле.

⚠️ Греп по репозиторию (`grep -r roborazzi`) отвечает на ДРУГОЙ вопрос. В KMP-репе плагин ставится помодульно, и соседний модуль с кадрами не даёт снять этот. Прецедент 2026-08-17: Roborazzi стоял в 4 модулях из 13, репо-греп вернул «есть», модуль правящегося экрана кадров не имел — цикл не был начат, а гейт прочитал отсутствие кадров как отсутствие проблем.

- Есть — работать по конвенциям проекта (пути golden'ов, имена тасок, helper'ы), свои не изобретать.
- Нет — setup из `references/roborazzi-setup.md`. Это правка build-конфигов и новая зависимость: **сначала сообщить главному агенту и получить добро**, не заводить молча. Главный решает не сам — выносит пользователю через `AskUserQuestion` (завести сейчас / отложить) в этой же задаче. Отложено — строка в `docs/todos/`; «предложил и забыл» отключает правило навсегда.

### 1. Фейковые состояния — до вёрстки

Content-composable принимает состояние параметром и не ходит в ViewModel. Набор состояний — в `PreviewParameterProvider`: loading · empty · error · success · **граничные** (длинный текст без пробелов, 40 элементов, пустая аватарка, число в 6 знаков, самая длинная локаль). Граничные — половина ценности цикла: именно они ломают вёрстку и именно их не показывает ручной прогон на happy-данных.

### 2. Матрица — аннотациями, не тест-файлами

На превью-composable вешаются multipreview-аннотации; тест-класс не пишется вообще, Roborazzi генерирует по тесту на вариант (`generateComposePreviewRobolectricTests`, см. `references/roborazzi-setup.md`).

```kotlin
@PreviewScreenSizes   // phone / foldable / tablet / desktop
@PreviewLightDark
@Composable
internal fun ProfileScreenPreview(   // не private: приватные превью сканер не берёт
    @PreviewParameter(ProfilePreviewStates::class) state: ProfileUiState,
) = AppTheme { ProfileContent(state = state, onAction = {}) }
```

**Потолок — примерно 40 снимков на экран.** Аннотации перемножаются: 4 размера × 7 масштабов шрифта × 2 темы × 3 состояния это 168 запусков Robolectric и десятки минут. `@PreviewFontScale` добавлять точечно — там, где текст правда рискует сломать раскладку, и лучше на одном размере. Компоненту хватает 1-2 размеров × темы.

Матрица задаётся аннотациями. Явная dp-сетка (400/610/900 × 400/500/1000 из Step 8 скилла `testing-setup`) — только если проект уже так устроен; смешивать два подхода в одном модуле не надо.

### 3. Снять

```bash
./gradlew :features:profile:recordRoborazziDebug          # Android-модуль
./gradlew :features:profile:recordRoborazziAndroidHostTest # KMP/CMP (androidHostTest)
```

### 4. Смотреть PNG самому — это и есть суть

Снимки лежат в каталоге из `roborazzi { outputDir }` (не задан — уехали в `build/`, см. setup). Найти — `Glob` по `<outputDir>/**/*.png`, имена генерирует плагин, угадывать их не надо. Дальше `Read` по путям.

Не «тесты прошли» — **прошедший record ничего не доказывает**, он лишь записал то, что нарисовалось, включая дефект. Пусто в каталоге при зелёном прогоне — тоже провал, а не успех. Что искать на картинках — `references/reading-screenshots.md`.

Снято N файлов — открыть как минимум: самый узкий размер, самый широкий, тёмную тему, fontScale ≥1.5 и каждое граничное состояние. Отчитываться «сделал» без прочитанного PNG нельзя.

### 4b. Сверка с эталоном

Есть с чем сравнивать — сравнивай, а не оценивай снимок в вакууме.

**Эталон** — макет из `DESIGN_SPEC` (поле со ссылкой на файл), экспорт из Figma или claude-design, скрин от пользователя, кадр «как было» до редизайна. Открыть `Read`'ом эталон и свой снимок **подряд, в одном сообщении** — различия видны на контрасте, по памяти они не ловятся.

Эталон обязан быть **растровым** (PNG/JPG): `Read` по HTML или SVG вернёт разметку, а не картинку, и сверка не состоится, хотя отчитаться о ней легко. HTML-выгрузка claude-design и экспорт Figma сначала рендерятся в PNG — рецепт в `references/web-playwright-visual.md`, раздел «Статичный макет без приложения»; для Android-спеки годится тот же браузерный рендер, он даёт композицию.

Эталоны и кадры «до» кладутся в **scratchpad-каталог сессии** — не в `outputDir` с golden'ами и не в репозиторий: это чужой или временный материал, ему там не место. В отчёт идут пути.

Сверять по порядку, от крупного к мелкому: набор и порядок блоков → пропорции и вертикальный ритм → типографическая иерархия (что крупнее чего) → цветовые роли и акценты → иконки и их размер → состояния. Расхождение фиксируется списком «эталон / у меня / решение», и каждое либо чинится, либо объявляется осознанным отступлением с причиной — молча разойтись с макетом нельзя.

Попиксельного совпадения не требуется и обычно не бывает: макет рисуется в одном масштабе, снимок снимается в другом, шрифты платформы отличаются. Цель — совпадение композиции и иерархии, а не diff по пикселям.

**Конкуренты — только по запросу.** Просят «сделай как у X» или «посмотри, как у конкурентов» — **файлы кадров даёт пользователь**; `@marketing-expert` отвечает за список конкурентов и разбор их листингов, но готовых PNG у него нет, и лезть в стор за ними самому — заход в чужой домен.

Из чужого кадра берётся **паттерн решения**: порядок шагов, что вынесено на первый экран, как показана цена. Не ассеты, не иконки, не тексты. Вёрстка, узнаваемо повторяющая чужой экран, не сдаётся, а переделывается — подписать её «это копия» недостаточно. Скрин конкурента — материал одного вызова: scratchpad-каталог сессии, не `outputDir`, не коммит. Не просили — не тащить: чужой продукт решает чужую задачу.

### 5. Итерация

Правка → `record` → снова `Read`. Круг стоит секунды и не требует пользователя — крутить до чистой вёрстки, а не отдавать первый вариант на ревью.

**«До» надо сохранить руками — `record` затирает.** Имена детерминированные, повторный прогон перезаписывает кадр, и восстановить его будет неоткуда. Перед следующим `record` — скопировать нужные кадры в scratchpad сессии (`before_<имя>.png`); альтернатива для Roborazzi — `compareRoborazzi*`, он сам кладёт diff-картинку рядом с golden'ом.

**Редизайн и UI-багфикс: кадр «до» снимается ПЕРЕД первой правкой.** Превью на текущем коде — снимок — и только потом трогать вёрстку. Начал править сразу — «до» больше не существует, и доказать исправление нечем.

### 6. Зафиксировать baseline

`verifyRoborazziDebug` перед сдачей, golden'ы — в коммит с кодом. Каталог растёт быстро; распухает — Git LFS.

### 7. Только теперь — реальный прогон

Устройство/эмулятор/браузер проверяют то, чего нет на картинке: флоу, жесты, анимацию, DI, реальные шрифты и вставки системных панелей. Ручной прогон **не отменяется** — он перестаёт быть способом искать съехавшие отступы.

## Что уходит в отчёт

Снимок — не только инструмент разработки, но и то, чем отчитываются. В ответ главному и пользователю:

- **Пути к снимкам**, которые ты открывал, и одной строкой что на каждом видно (размер, тема, состояние). Пользователь откроет их сам — это дешевле, чем ставить сборку на телефон.
- **До/после** — для багфикса и редизайна обязательно парой: снимок с дефектом и снимок после правки. Одна картинка «после» не доказывает, что баг ушёл.
- **Расхождения с эталоном**, которые оставлены осознанно, и почему.
- **Что снимком не покрыто** — состояния, которые не удалось собрать фейком, и всё из раздела «Границы».

## Ручные скрины заменяются программными везде, где есть доступ к коду

Если экран собирается из нашего кода, снимать его руками на устройстве не нужно — то же самое снимается циклом, быстрее и в любом количестве вариантов:

- **Показать вёрстку и состояния** пользователю вместо «собери и поставь на телефон». Работу флоу, жестов и данных PNG не показывает — за этим остаётся ручной прогон.
- **Иллюстрации к докам и баг-репортам** — воспроизводимо, с точным состоянием.
- **Локали** — все языки за один прогон: на Android `@Preview(locale = "ar")` (или свой multipreview-набор локалей) и qualifier `RuntimeEnvironment.setQualifiers("+ar")` в ручном тесте, на web — `test.use({ locale: 'ar' })` либо отдельный Playwright-проект на локаль. Руками их не отщёлкивают.
- **Исходные кадры для стор-креатива** — снимаются кодом на нужных размерах и с идеальным контентом. Дальше кадры уходят в оформление (`@design-expert` по брифу `@marketing-expert`): маркетинговый креатив — это кадр плюс подпись и фон, а не голый скриншот. Требования стора к размерам кадров проверяются у первоисточника, а не по памяти.

Руками остаётся то, где кода нет или нужен живой рантайм: чужое приложение и конкуренты, реальные шрифты и системные панели устройства, жесты и анимация в движении, проверка на конкретной модели.

## Багфикс-режим

1. Воспроизвести баг **на картинке**: то состояние, тот размер, та тема, тот fontScale. PNG с видимым дефектом = RED.
2. Баг на PNG не воспроизвёлся — он не визуальный либо зависит от данных, тайминга или устройства: скриншот-репро не годится, возвращаться к `systematic-debugging` и обычному репро.
3. Фикс (пишет доменный специалист) → `record` → сравнить старый и новый PNG.
4. Golden с дефектом не оставлять записанным как эталон — это узаконивает баг.

## Детерминизм — иначе golden мигает

Обязательный минимум: пин часов при бесконечных анимациях и индикаторах загрузки · фейковый image loader вместо сети · фиксированные дата, seed, порядок списка · `GraphicsMode.NATIVE` + hardware-рендер. Детали и грабли — `references/roborazzi-setup.md`.

## Web

Playwright `toHaveScreenshot` на матрице viewport'ов — `references/web-playwright-visual.md`. Отдельный случай: Compose Multiplatform в браузере рисует в `<canvas>` — DOM-локаторов нет, работают только координаты, console-assert и сам скриншот.

## Границы

Скриншот доказывает **раскладку и стиль в снятом состоянии**. Он не доказывает: что данные пришли, что клик сработал, что картинка декодировалась (фейковый loader рисует заглушку), что на реальном устройстве те же шрифты и insets. Покрытие, которое агент себе приписал сверх этого, — мнимое; так и помечать в отчёте.
