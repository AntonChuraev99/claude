# Task Gate — Definition of Done

Скилл-чеклист, проверяет, что завершённую задачу можно безопасно закрыть. Источник правил — Definition of Done в глобальном `~/.claude/CLAUDE.md`. Единица работы — **задача** (фича/фикс), не сессия: за сессию с несколькими задачами скилл запускается несколько раз, по разу на задачу.

## Зачем это нужно

После сложной задачи легко забыть обязательный пункт: `@doc-writer COMPLETE`, обновить `~/.claude/stats/doc-writer.md`, дописать `INDEX_ROW` в `docs/solutions/INDEX.md`, сделать коммит через `/commit`. Каждый пропуск ломает compound effect. Запускай **до** финального ответа «всё готово».

**Императив (CLAUDE.md → Definition of Done):** на любой задаче, где менялся код или конфигурация, скилл **обязан** быть запущен перед финальным ответом. Без него `STATS_ROW` не пишется, `INDEX_ROW` не дописывается — следующая сессия не найдёт решение, `## Deferred Work` не сверяется. Вопрос-ответ и read-only анализ — без gate. Аудит 2026-05-27 (ещё под именем end-session): запускался в 14% подходящих сессий — имя «конец сессии» мешало запускам mid-session, отсюда переименование. Запуск ~10 сек, цена пропуска — недели потерянной памяти.

## Когда скилл активируется

**Триггеры:** задача завершена — «готово», «фича готова», «фикс готов», «финализируй»; конец сессии — «заканчиваем», «end session», «можно закрывать?», «wrap up»; главный агент считает задачу завершённой; после последней правки + валидации. **Не активируется:** посреди отладки/рефакторинга/открытых TODO; пользователь сказал «продолжим завтра» без просьбы зачехлить.

## Re-entrancy — несколько прогонов за сессию

Каждый прогон gate скоупится **диффом текущей задачи**, не всей сессии. Состояние между прогонами — файл `task-gate-state.json` в session-scratchpad (директория из системного промпта):

```json
{ "lastGateSha": "<HEAD на момент прошлого пройденного gate>",
  "reviewedSha": "<HEAD на момент последнего 2.3b, закрытого без ❌>",
  "onceChecks": { "hookSetup": true, "activeHygiene": true, "rollup": true },
  "deferredChecks": ["2.3b", "step3", "step4"] }
```

**BASE_SHA** для diff-скоупа (2.2 impact, 2.8 TODO-scan, L1 в 2.0, `Шагов: N` для doc-writer) — первый доступный: (1) `lastGateSha` из state-файла; (2) START_SHA начала сессии, если известен; (3) нет ни того ни другого → рабочее дерево без `--base`.

**После пройденного gate** (вердикт READY / READY WITH WARNINGS, включая auto-commit): записать `lastGateSha = HEAD` в state-файл. **Once-per-session проверки** (помечены `[once]` ниже) — на повторном прогоне скипаются со статусом `✅ once (done earlier)`: hook setup (2.9), active hygiene (2.4), rollup `stats.py` (2.9).

**`deferredChecks`** — долг `lite`-прогонов (2.3b, Step 3, Step 4). Пункт отработал на `full` → убрать его из массива. Массив непуст → Step 6 не запускается (см. его гарды): отложенное не уезжает в merge молча.

**`reviewedSha`** — граница уже отревьюенного (2.3b). Пишется только на `full`-прогоне и только когда ревью закрылось без `❌`; на `lite` не трогается вовсе. Даёт инкрементальный скоуп повторным `full`-прогонам одной ветки: третий прогон ревьюит приращение, а не ветку заново. **Покрытие при этом не рвётся:** `lite`-прогоны `reviewedSha` не двигают, поэтому всё, что они закрыли, лежит внутри диапазона `reviewedSha..HEAD` и попадает в ближайший `full` (инвариант из improvements 2026-08-19: задачи, закрытые прошлыми `lite`, из ревью не выпадают).

## Workflow

5 шагов **последовательно**, статус (`✅`/`⚠️`/`❌`) после каждой проверки, финальный отчёт в конце: Step 1 — Task Snapshot (+ выбор режима); Step 2 — Definition of Done Checks; Step 3 — Sub-agent Sanity Check; Step 4 — Recommendations Pull; Step 5 — Commit & Final Report.

**Исключение из последовательности — 2.0 Review fan-out:** ревью-агенты запускаются фоном первым делом в Step 2 и работают, пока идут 2.1–2.8; их результаты принимаются в 2.3b и 2.9. Всё остальное по-прежнему по порядку.

**Гейт двухрежимный** (2026-08-19): `full` гоняет всё, `lite` — только проверки, которые ловят баги. Режим выбирается в Step 1, печатается в snapshot и в финальном отчёте. Дальше скилл **останавливается и ждёт подтверждения пользователя**; получено → Step 6 — MR & Merge (обновление базы, push, MR/PR, merge, уборка).

## Step 1 — Task Snapshot

Собрать: BASE_SHA (см. Re-entrancy) и изменённые файлы задачи (`git status` + `git diff --stat <BASE_SHA>`); вызванные специалисты; путь к активному документу в `docs/active/` (может отсутствовать — документ создаётся не на каждую задачу).

Печатать `📋 Task snapshot:` + строки `Base`, `Files changed`, `Agents used`, `Active doc`, `Mode`. Повторный прогон за сессию → добавить строку `Gate run: #N in session`.

### 1.1 Режим гейта — `full` или `lite`

**`full`** — если верно **хотя бы одно**: дифф ≥ 5 файлов · появился новый модуль, миграция или новый публичный контракт (API, схема, событие аналитики) · тронут деплой, инфраструктура или конфигурация окружения · **этот прогон — последний перед мержем** (по его подтверждению запускается Step 6) · дифф трогает `~/.claude/{CLAUDE.md,agents,skills,settings.json,rules,review-rules}` · пользователь попросил полный прогон.

**`lite`** — всё остальное: правка ≤ 4 файлов в существующем коде без нового контракта и без деплоя.

**Что гоняет `lite`:** 2.0 review fan-out — в усечённом виде: контекст-пакет, L1 и, по его находкам, один L2 (осей 2.3b нет) · 2.1 validation · 2.2 impact scan · 2.2b скриншот-цикл (если дифф трогал вёрстку — правило не ослабляется режимом) · 2.3 self-check · 2.4–2.7b (они самоскипаются в `✅ N/A`, если `@doc-writer` за задачу не вызывался; вызывался — гонятся полностью, кроме вложенных `[once]`-подпунктов, включая ожидание COMPLETE до Step 5) · 2.8 deferred work · 2.9 целиком — L1 static, **L2 по обычному триггеру** (вывод L1 непуст → `@bug-pattern-reviewer`; инвариант `CLAUDE.md` → «Bug-pattern gate», режимом не снимается) и L3 process · 2.9 Hook setup `[once]` (это гарантия, что pre-commit с L1 стоит, а не учёт) · 2.10 improvements log (его триггер и так форсит `full`, в `lite` — `✅ N/A`) · Step 5 commit.

**Что `lite` откладывает:** 2.3b (diff review свежим агентом), Step 3 (sub-agent sanity) и Step 4 (recommendations pull) — строкой `⏸ deferred to pre-merge (full) gate` в отчёте. Отложенное не растворяется: оно **записывается в `deferredChecks` state-файла**, и Step 6 с непустым `deferredChecks` не запускается (гард — Step 6). 2.3b на `full`-прогоне ревьюит **всё, что накопилось с прошлого успешного ревью** (база — по правилу 2.3b: `reviewedSha`, иначе `origin/<транк>`), а `lite`-прогоны `reviewedSha` не двигают — поэтому отложенные ими задачи из ревью не выпадают. Бухгалтерия с меткой `[once]` в `lite` не запускается вовсе.

**Что режим НЕ ослабляет ни при каких условиях:** 2.2b (вёрстка проверяется картинкой), 2.8 (отложенный функционал), 2.9 static-HIGH как блокер, запрет коммитить мимо `/commit`.

## Step 2 — Definition of Done Checks

9 пунктов CLAUDE.md → «Definition of Done» + п. 2.3b (diff review двумя осями) + п. 2.9 (bug-pattern review). Прогоняй по порядку, статус одной строкой — **кроме 2.0: он стартует первым и работает фоном под остальными пунктами.**

### 2.0 Review fan-out (старт ревью — до остальных проверок)

Ревью-агенты — самая долгая часть гейта, а их находки нужны только к финальному отчёту. Поэтому они стартуют **первыми и фоном**, а 2.1–2.8 идут, пока они работают; результаты принимаются на своих местах — в 2.3b и 2.9. Раньше 2.3b и 2.9 стояли по порядку шагов и складывались во времени, хотя между ними нет зависимости: линзы разные, выходы разные.

1. **Контекст-пакет — один раз на все оси.** `references/diff-review-axes.md` → «Контекст-пакет»: главный собирает дифф в `<session-scratchpad>/review-package-<sha>.md` и раздаёт агентам **путь**, не содержимое.

   **Пакет собирается по базе 2.3b, и его диапазон записан в шапке.** У L2 база своя (`BASE_SHA`), и совпадают они не всегда: `reviewedSha` двигает базу 2.3b вперёд независимо от `lastGateSha`. Базы разошлись → **собрать L2 второй пакет** той же командой от его базы, отдельным файлом. Это ещё один `git diff` главного — но он всё равно дешевле, чем холодный сбор внутри агента, и сохраняет выигрыш (a) на всём фан-ауте, а не на двух третях. Чего делать нельзя — отдать L2 пакет чужого диапазона: агент примет его за свой скоуп и отревьюит не то, о чём отчитается.
2. **L1 static — до фан-аута, один прогон на гейт.** Вывод сразу в файл рядом с пакетом:

   ```bash
   python ~/.claude/review-rules/run.py --base <BASE_SHA> --changed-only --json \
     --log ~/.claude/stats/review-rules-events.jsonl --entry endsession \
     > <session-scratchpad>/l1-<short-sha>.json
   ```

   Детерминированно, без LLM, секунды; `--entry endsession` — исторический лейбл, не менять. Гонится здесь, потому что его вывод — триггер L2; путь к этому JSON идёт в бриф L2, агент его читает, а не перезапускает. Разбор находок и статусы — 2.9, второй раз команду не запускать.
3. **Фан-аут — все вызовы `Agent` одним сообщением.** У `Agent` **нет** параметра `run_in_background` (он есть у `Bash`): вызов и так возвращается сразу, результат приходит уведомлением. «Фоном» здесь означает ровно одно — **отправить все вызовы одним сообщением и идти дальше в 2.1**, не дожидаясь ответов.
   - **Оси 2.3b — по умолчанию ОДИН вызов** `Agent(subagent_type="general-purpose")` с обеими осями в брифе и раздельными секциями в ответе; модель **не** понижать, бриф несёт Spec-ось. Два отдельных вызова — только по порогу 2.3b (дифф >30 файлов либо трогает деньги, безопасность, деплой): тогда Standards получает `model="sonnet"` (аудит по готовому чеклисту — прецедент improvements 2026-06-01: «opus редко даёт прирост на research/audit»), Spec — модель сессионную, на нём не экономим.
   - **L2** — `Agent(subagent_type="bug-pattern-reviewer")`, **только если L1 дал находку в режиме `static`** (триггер сужен, см. 2.9). Модель у него своя, во frontmatter.
   Итого типичный фан-аут — **два вызова** (оси + L2), а не три; при чистом `static` — один.
4. **Отсечки времени — три снимка `date +%s`, каждый вокруг своего вызова:** в самом начале Step 1 (для `gate`), вокруг `run.py` в п. 2 (для `l1`), перед этим фан-аутом и при приёме последнего результата в 2.9 (для `review`). Числа держать в тексте прогона и подставить в 5.2 **литералами**: переменные шелла между вызовами `Bash` не переживают.

**Режим `lite`** → осей 2.3b нет (`⏸ deferred to pre-merge (full) gate`), фан-аут состоит из одного L2 по его триггеру (`static`-находка), а пакет собирается по базе L2 (`BASE_SHA`). `static` чист → в `lite` фан-аута нет вовсе.

**Fail fast гасит только оси 2.3b, не L2.** Его условия (режим `full`, резолвится ли база 2.3b, непустой дифф) принадлежат 2.3b: провал любого — оси не спавнятся, причина печатается в 2.3b. **L2 живёт по своему триггеру — находке L1 в режиме `static` — и режимом гейта не снимается** (инвариант `CLAUDE.md` → «Bug-pattern gate»): ни `lite`, ни нерезолвящийся `origin/<транк>` его не отменяют.

**Ревью-агенты read-only.** Агент не наследует PreToolUse-хуки главного, поэтому запрет на запись держится только брифом — строка «ничего не редактируй, не коммить, не запускай сборки и тесты; твой продукт — отчёт» обязательна в каждом. У `@bug-pattern-reviewer` есть ещё и ограничение инструментов, но **на него не полагаться**: frontmatter объявляет `Read, Grep, Glob, Bash`, а рантайм-реестр агентов показывает у него дополнительно `Write, Edit` — расхождение не в пользу запрета.

Статус: `✅ N agents dispatched (<оси>)` / `⏸ lite — only L2` / `⏸ lite — nothing dispatched (static clean)` / `⚠️ not dispatched (<причина>)`.

### 2.1 Validation

Сборка/тесты прошли. Не была сборка → `⚠️ unverified` + рекомендация запустить. Тесты — аналогично.

### 2.2 Impact Scan

Все зависимости обновлены: импорты, использования, тесты. Проверять через `ast-index` по именам ключевых сущностей, изменённых **в этой задаче** (дифф от BASE_SHA): `ast-index changed --base <BASE_SHA>` даёт список изменённых символов, дальше `usages` / `refs` / `implementations` по каждому. `Grep` — fallback на regex, строковые литералы и файлы вне индекса; `rebuild`/`update` не запускать. Правка в одном файле без новых или переименованных символов — отметить, что сканировать нечего.

### 2.2b Скриншот-цикл (только если дифф трогал вёрстку)

Дифф содержит UI-файлы (Compose-composable, `.tsx`-компоненты, стили) → в отчёте **таблица по поверхностям**, а не общий вердикт по задаче: строка на каждый экран или компонент, который задача изменила **либо впервые сделала достижимым**; в строке — путь к кадру, который агент открывал, и что на нём видно, либо `не снят` + причина. **Кадры соседней поверхности чужую строку не закрывают.** Инвариант CLAUDE.md → «Вёрстка — проверяется картинкой, а не пользователем», процедура — скилл `screenshot-driven-ui`.

**Инфраструктура проверяется по МОДУЛЮ изменённого файла, а не по репозиторию.** Roborazzi подключается в `build.gradle.kts` модуля и держит голдены в `<module>/src/androidHostTest/roborazzi/`; «в проекте кадры есть» не говорит ничего про этот модуль:

Снипет ниже покрывает **только Compose-модули**; для web-диффа (`.tsx`, стили) инфраструктура проверяется наличием Playwright-конфига и каталога снапшотов рядом с изменённым компонентом — пустой список `NONE` на web-диффе означает «проверка не проводилась», а не «инфраструктура есть».

```bash
git diff --name-only <BASE_SHA> -- '*.kt' | grep -Ei 'screen|content|dock|bar|sheet|card|row|panel|designsystem' |
while read f; do d=$(dirname "$f"); while [ "$d" != "." ]; do [ -f "$d/build.gradle.kts" ] && { echo "$d"; break; }; d=$(dirname "$d"); done; done | sort -u |
while read m; do [ -d "$m/src/androidHostTest/roborazzi" ] && echo "OK   $m" || echo "NONE $m"; done
```

- Все строки таблицы несут открытый кадр → `✅`.
- Модуль в списке `NONE` → `⚠️ no screenshot infra: <модуль>` + развилка «завести сейчас / отложить» вынесена пользователю через `AskUserQuestion`, отложенное — строкой в `docs/todos/`.
- Строка без кадра и без причины → `❌` : вёрстка не проверена, а не «проверена ручным сценарием».

**Впервые достижимая поверхность идёт в таблицу, даже если её код не менялся.** Новый route, новая кнопка, новый ряд входов или deep link на существующий экран — это отгрузка экрана в новой роли: он мог годами жить редко открываемым и не выдерживать роль главной двери. Ищется в диффе навигации: новый `AppNavRoute` либо новый call-site `navigateTo*` на существующий экран.

> Прецедент 2026-08-17 (`feat/ux-overhaul`): ветка пристроила к экрану Analyze четыре новые двери, сам экран при этом почти не менялся. Гейт спросил «есть ли инфраструктура в проекте» — Roborazzi стоял в 4 модулях из 13, ответ «есть», люк `⚠️ no screenshot infra` не открылся ни разу. За ветку сняли десятки кадров дверей и **ноль** кадров того, куда двери ведут; шесть карточек типа источника занимали ~336dp — весь первый экран — и это увидел владелец, а не гейт.

### 2.3 Self-check vs FAILURE

Результат соответствует FAILURE-критериям Prompt Contract (архитектура, хардкод, error handling). Контракт не озвучивался → `⚠️ no Prompt Contract` + попросить подтвердить.

### 2.3b Diff review свежим агентом (Standards + Spec)

Инвариант CLAUDE.md → «Роль главного агента»: перед «готово» дифф ревьюит **свежий субагент** — он видит только дифф и критерий, не видит рассуждений, которые к нему привели. Метод — две независимые оси (скилл `code-review`):

- **Standards** — соответствует ли код документированным правилам проекта + smell baseline (12 смелов Фаулера).
- **Spec** — реализует ли дифф то, о чём просили (активный документ задачи / Prompt Contract): пропущенные требования, scope creep, неверно понятые требования.

**Когда запускать — два условия, оба обязательны** (сужено 2026-08-19; было «на каждом прогоне, где дифф трогает код или конфигурацию» — ревью запускалось на правках документации и правил, где smell baseline неприменим, и повторялось на каждой задаче внутри одной ветки):

1. **Режим `full`.** В `lite` — не запускать, строка `⏸ deferred to pre-merge (full) gate`. Ветка обычно живёт дольше одной задачи, а `full` наступает там, где она заканчивается мержем, — ревью платится один раз за ветку, а не за каждую задачу внутри неё.
2. **Дифф непуст.** Наличие исполняемого кода определяет не «запускать или нет», а **сколько агентов**:

   - **Код есть** → smell baseline применяется. Считается кодом: исходники (`.kt .kts .java .swift .ts .tsx .js .jsx .py .rb .go .rs .php .sql .sh .ps1`), build-скрипты (`*.gradle`, `*.gradle.kts`, `Podfile`, `package.json` в части скриптов и зависимостей) и **конфигурация, исполняемая внешней системой** (`.github/workflows/**`, `.gitlab-ci.yml`, `wrangler.*`, `firebase.json`, `*.tf`, правила безопасности БД). Число агентов при этом определяет порог ниже, а не сам факт кода: дефолт — один.
   - **Кода нет** — правила самого харнесса (`~/.claude/**`), `docs/**`, любые `.md`, `review-rules/*.yaml`, локализация, статические ассеты → один агент при любом размере диффа. Standards на таком диффе = сверка с документированными правилами (`CLAUDE.md` и его инварианты, конвенции репозитория) плюс целостность ссылок на скиллы, агентов и файлы; **smell baseline Фаулера не применять** — он про код. Spec — без изменений, это единственный механизм, ловящий «сделано не то, о чём просили».

   Решение 2026-08-19 после того, как ревью диффа правил (два агента) нашло в нём три блокера уровня high: правки инвариантов без внешнего взгляда не отгружаются, но платятся одним холодным контекстом, а не двумя.

`/code-review` уже прогонялся по этой задаче → `✅ verified by /code-review`.

**База ревью — вся ветка, а не дифф задачи; на повторном `full` — приращение.** Первая доступная:

1. **`reviewedSha`** из state-файла, если он предок HEAD (`git merge-base --is-ancestor <reviewedSha> HEAD`) — граница уже отревьюенного. Второй и третий `full`-прогон одной ветки смотрят только новое, а не ветку заново (Target improvements 2026-08-19: «не больше одного спавна 2.3b на ветку»; повторный полный проход — это тот же спавн, оплаченный дважды).
2. **`origin/<транк>`** на merge-bound ветке (транк — из `~/.claude/config/protected-branches.local.json`): первый `full` ревьюит то, что реально уедет в MR, включая задачи этой ветки, закрытые прошлыми `lite`-прогонами.
3. **`BASE_SHA`** — ветка не merge-bound (согласованная работа в транке, репозиторий профиля `~/.claude`).

Диапазон — от `git merge-base <база> HEAD` до **рабочего дерева**, не до HEAD. Две причины разом: влитый в ветку транк (Step 6.0) в ревью не попадает (чужие коммиты не наши), и ревью видит ещё не закоммиченное — 2.0 идёт до Step 5, поэтому `<база>...HEAD` на типичном прогоне отдал бы ревьюерам пустой дифф. Механика и проверка — `references/diff-review-axes.md` → «Контекст-пакет».

**`reviewedSha` двигается только на успехе:** ревью закрылось без `❌` → записать `reviewedSha = HEAD` рядом с `lastGateSha` (5.2). Был `❌` → **не записывать**, следующий прогон обязан посмотреть тот же диапазон ещё раз. `lite`-прогоны `reviewedSha` не трогают.

**И только если с момента ревью ничего не изменилось.** Ревьюилось рабочее дерево на момент 2.0, а `reviewedSha = HEAD` пишется в 5.2 — между ними лежат 2.4–2.7b (доки `@doc-writer`), фиксы `static` HIGH, правки по self-check и коммит 5.1. Всё это уехало бы в коммит со штампом «отревьюено», ни разу не показанное ревьюеру, а следующий `full` начал бы уже за этой границей. Поэтому — сверка отпечатка:

```bash
git diff "$MB" | sha1sum        # снять в 2.0, сразу после сборки пакета
git diff "$MB" | sha1sum        # повторить в 5.2, ДО записи reviewedSha
```

Отпечатки совпали → писать `reviewedSha = HEAD`. Разошлись (что-то дописано после фан-аута) → **не писать**, в отчёт `⚠️ reviewedSha not advanced: diff changed after review`. Проверка `git status --porcelain` этот случай не ловит: 5.1.1 как раз всё коммитит, и дерево к 5.2 чистое.

**Сколько агентов.** Дефолт — **один** с обеими осями; два — только если дифф >30 файлов **или** трогает деньги, безопасность, деплой (полное правило и обоснование — `references/diff-review-axes.md` → «Две оси, один агент по умолчанию»). Дифф без исполняемого кода — один агент при любом размере, smell baseline не применять.

**Повторный `full` по той же ветке** (`reviewedSha` уже записывался) → в бриф добавляется строка convergence: новые находки уровня суждения и стилистики не репортить, только корректность и требования. Второй проход по тому же коду обязан сходиться, а не набирать новый слой замечаний.

**Как:** агенты уже запущены в 2.0 (fail fast, контекст-пакет, модель по оси — там же). Здесь — **приём результатов**: дождаться агентов, напечатать отчёты **раздельно по осям**, не сливая и не переранжируя между ними. Секция `## Optional` печатается свёрнутой — «optional: N пунктов», в починку не идёт.

**Триаж перед починкой — обязателен, делает главный сам.** Находка (с любой оси и от L2) идёт в фикс, только если её `failure_scenario` проверен по коду: открыть названный `file:line`, пройти сценарий, убедиться, что результат действительно неверный. Проверка стоит одного `Read`; агент-фиксер на непроверенной находке стоит холодного контекста плюс правки, которая чинит несуществующее.

- Сценарий подтвердился → в фикс.
- Сценарий не воспроизводится по коду → находка **отбрасывается**, строкой в отчёт: `triaged out: <находка> — сценарий не подтверждён`. В `docs/todos/` не класть: там только заблокированное внешним событием, а не отвергнутые гипотезы.
- Проверить нельзя без прогона (рантайм: гонка, insets, анимация, видео) → не фикс, а пункт в `VERIFY` с конкретным сценарием прогона.

**Чинит один агент пачкой, не агент на ось.** Все подтверждённые находки уходят одним брифом одному профильному специалисту (домен — по файлам фикса, правило `CLAUDE.md` → «Прод-код пишет специалист»); находки разных доменов — по агенту на домен, но не по агенту на ось и не по агенту на находку. Паттерн `/code-review --fix`: одна починка на один проход ревью.

Ось не вернулась (агент упал, отменён) → `⚠️ diff review incomplete: <ось>`, `reviewedSha` не двигать **и `2.3b` оставить в `deferredChecks`**. Правило Re-entrancy «пункт отработал на `full` → убрать из массива» здесь не применяется: отработал прогон, а не проверка. Иначе гард Step 6 пропустит в merge ветку, которую свежий ревьюер так и не увидел.

Полные промпты, smell baseline, порядок поиска Spec-источника, правила «проект перекрывает baseline» и «пропускать то, что ловит линтер» → [`references/diff-review-axes.md`](references/diff-review-axes.md).

Статус: `✅ clean (2 axes, 1 reviewer)` / `✅ clean (2 axes, 2 reviewers — <причина порога>)` / `⚠️ N standards + M spec findings (+K triaged out, optional: L)` / `❌ spec: требование не реализовано` (блокер — задача не делает того, о чём просили). Standards-находки уровня суждения gate не блокируют; их место — в отчёт.

### 2.4 `@doc-writer` COMPLETE

Запущен ли COMPLETE и **получен ли результат**?

**Критерий обязательности** (`~/.claude/CLAUDE.md` → «Документирование»). Документ обязателен, если задача набрала **хотя бы один** признак — проверяются по факту диффа и хода работы, не по предварительной оценке:

- понадобилось 2+ итерации либо начальный план оказался неверен;
- тронуто 5+ файлов, появился новый модуль или выполнена миграция;
- recurring bug либо исправление, влияющее на всё приложение (перф, архитектура, security);
- инфраструктурный фикс с нетривиальной причиной (CSP, конфиг Firebase, DI, регионы, сериализация);
- пользователь попросил задокументировать.

Ни одного признака → `✅ skipped (rule)`.

**Запустить** при необходимости: `Agent(subagent_type="doc-writer", run_in_background=true)`. **В prompt передать:** GOAL; путь к активному документу; путь к project memory; hard scope guard; **`Шагов: N`** (правила подсчёта — `references/calibration.md` → «Источник `iterations`»; считать шаги **этой задачи**, от BASE_SHA, не всей сессии); готовый `git diff --name-only <BASE_SHA>..HEAD -- ':(exclude)docs/*'`; 3–5 строк key-findings; **инструкцию финальной архивации (Шаг 7):** «после сбора метрик перемести активный документ в `docs/archive/` и верни `ARCHIVED:` путь» — только при статусе `Done` (Partially Done / Deferred → остаётся в `docs/active/`). Скилл оценивает `N` по transcript: code-edit + build/test + делегации, исключая `/commit`, `/task-gate`, `@knowledge-scout`, `@doc-writer` фазы, todo updates, чтение файлов. Не нужен → `✅ skipped (rule)`.

**Why `Шагов: N`:** без поля counter падает на fallback `grep -c "### Итерация "`, а он измеряет частоту делегирования, а не реальный объём работы. Аудит 2026-05-11 показал занижение до −90% на коротких задачах.

**Active hygiene `[once]` (анти-свалка `docs/active/`).** Раз за сессию, на первом прогоне gate. Быстрый scan: (а) файлы со `**Статус:** Done` в шапке, всё ещё лежащие в `docs/active/` → доархивируй `mv docs/active/<f> docs/archive/<f>`; (б) файлы с `In Progress` в шапке, но заполненными `## Выводы` / `Done` в теле → выровняй шапку на `**Статус:** Done` и перенеси в `docs/archive/`. Ловит COMPLETE прошлых сессий, не довёдшие Шаг 7. Документ остаётся в `docs/active/` только при `In Progress` / `Partially Done` / `Deferred` / `Planned`. Прецедент 2026-06-11: 149 готовых задач застряли в `docs/active/` (154 файла), дайджест показывал ложный фронт работ.

### 2.7b Документация уезжает вместе с кодом (`DOCS_WRITTEN`)

Документы, написанные субагентами, обязаны попасть в тот же коммит и merge request, что и код задачи. Субагенты git не трогают — стейджит и коммитит главный, поэтому без явной проверки документ остаётся в рабочем дереве и расходится с веткой.

**Действие:**

1. Собрать пути из строк `DOCS_WRITTEN:` всех вызовов `@doc-writer` за эту задачу (фазы INIT / UPDATE / COMPLETE — у каждой своя строка). Плюс `ARCHIVED:` — путь после переезда в `docs/archive/`, старого пути в `docs/active/` в дереве уже нет.
2. Для каждого пути: `git status --porcelain -- <path>`. Пусто и файл существует → уже в коммите или не изменён. Непусто → файл не в индексе, к коммиту его добавляет Step 5.
3. **Файл не существует ни на диске, ни в git** → `❌` и не закрывать gate: `@doc-writer` отрапортовал о записи, которой не было. Класс известный (прецедент 2026-07-14), поэтому это блокер, а не warning.
4. **`docs/` под gitignore** (проверка: `git check-ignore -q docs` — код 0) → `⚠️ docs/ gitignored — документация физически не может уехать в MR`. Не блокер: в части проектов так и задумано. Строкой в финальный отчёт, чтобы расхождение было видно.

**Фоновый `@doc-writer` может закончить после коммита.** COMPLETE запускается с `run_in_background: true`, и Step 5 способен закоммитить раньше, чем придёт `DOCS_WRITTEN`. Поэтому: результат COMPLETE **дождаться до** Step 5. Уже закоммитили, а файлы пришли позже → `git add` этих файлов и `--amend` последнего коммита, если он ещё не запушен; запушен — отдельный коммит `docs: <slug>` в ту же ветку. Молча оставить документ вне MR нельзя.

`@doc-writer` не вызывался за задачу → `✅ N/A`.

### 2.8 Deferred-work integrity (TODO / FIXME / docs/todos/)

Проверить, что в коде нет «потерянных» TODO/FIXME, отложенный функционал имеет `docs/todos/<...>.md`. Источник — `~/.claude/CLAUDE.md` → «Отложенный функционал».

Кратко:
1. `git diff -U0 <BASE_SHA>` (нет BASE_SHA → `HEAD`) по code-расширениям → grep `\b(TODO|FIXME|STOPSHIP):` в `^+` строках (test-файлы исключены).
2. Категории: 0 совпадений → `✅ no unbacked TODO`; с `// Pending: docs/todos/<file>` anchor + файл существует → `✅ TODO anchors valid`; без anchor или файл отсутствует → `⚠️ unbacked TODO` / `⚠️ broken Pending anchor`.
3. Unbacked TODO — gate не блокируется (warning), но 5.1.1 Auto-commit **не запускать** до `AskUserQuestion` (Create docs/todos / Delete TODO / Override / Defer).
4. `docs/todos/INDEX.md` есть → проверить `## Open` ссылки + memory desync.
5. `/commit` уже был в рамках этой задачи со своим scan → `✅ verified by /commit at <sha>`.

Полные Bash-команды, exclude-паттерны, шаблон `docs/todos/<...>.md`, опции `AskUserQuestion` → `references/deferred-work-scan.md`.

### 2.9 Bug-pattern review (L1 static + L2 reviewer + L3 process gate)

Сверка diff с реестром повторяющихся багов `~/.claude/review-rules/` — система против «тех же багов каждую сессию» (system bar не покрашен, анимация, отступы, регион деплоя, субагент выпилил фичу). Источник — `~/.claude/review-rules/README.md`.

- **L1 (всегда, дёшево, без LLM):** Stop-хук уже прогнал L1 по ходу сессии и залогировал. Полный прогон по задаче сделан в **2.0** (там же полная команда; нет BASE_SHA → без `--base` = рабочее дерево) — здесь разбирается его вывод, команда второй раз не запускается. `static` HIGH → **❌ blocker** (как pre-commit): выровнять до закрытия gate, auto-commit 5.1.1 **не запускать**. `runtime` WARN → в отчёт.
- **L2 (триггер — находка L1 в режиме `static`):** `static`-находка есть → агент уже запущен в 2.0, здесь — **приём результата**. В брифе обязаны быть **и base ref, и путь к контекст-пакету**: без base ref агент по своему контракту легально уходит ревьюить рабочее дерево, то есть молча меняет скоуп. Возвращает BLOCKERS / RUNTIME RED-FLAGS (confidence) / PROCESS GATE ARMED / NEW_RULE_CANDIDATE / `LOG_ROW:`. `static` чист → L2 не спавнится (`✅ skipped (static clean)`), даже если `runtime`-правила сработали. Агент сам пишет своё L2-событие в лог.

  **Почему триггер сужен (2026-08-31).** Был «вывод L1 непуст», а он непуст практически всегда: замер `stats/review-rules.md` на 2026-08-30 — 5202 прогона L1, 10 блокировок, и **ни одно `runtime`-правило за всю историю не дало ни одной блокировки** (топ по срабатываниям: 5972 / 5535 / 4765 fires при `blocks=0` и est-FP 84–100%). L2 в такой схеме работал не углублённой проверкой, а дорогим фильтром собственного шума — 315 confirmed против 785 dismissed, точность 29%. Ценность даёт `static`-режим, по нему и триггерим. `runtime`-срабатывания не пропадают: они печатаются строкой в отчёте (пункт выше) как справка, но дорогого агента не поднимают. Диагноз и замер — `docs/backlog/review-rules-noise-reduction.md`.
- **L3 process-gate (всегда, дёшево):** пройти armed process-вопросы (из L2 либо прочитать `process-gate.yaml` сам): молча ли удалена user-facing функция? тронут деплой → регион/аккаунт/smoke сверены? субагент в scope, не коммитил? баг невоспроизведён, а патчишь? Любой неотвеченный armed-вопрос severity high → `⚠️` в отчёт (боль #5 — не отгружать молчком; при потере функции — `AskUserQuestion` ДО завершения).

## Step 5 — Commit & Final Report

### 5.1 Commit Verification

`git status --porcelain` непустой → проверить, был ли `/commit` в рамках задачи. Был + новые правки или не был → 5.1.1 (auto-commit при выполнении условий), иначе предложить запустить `/commit`. Чисто + коммит был → `✅ commit ok`. Чисто + не было → `✅ no changes to commit`.

**Никогда** не вызывать `git commit` через Bash — только `/commit`.

**5.1a Готовность к merge (проверка, без действий).** Коммит — не конец: задача закрывается **влитым** MR/PR (`CLAUDE.md` → «Защищённая ветка и worktree»). Здесь только собрать факты для отчёта, push и MR — в Step 6.

Проверить: (1) `git rev-parse --abbrev-ref HEAD` — не защищённая ветка (иначе `⚠️ committed to trunk`, Step 6 не запускать); (2) апстрим — `git rev-parse --abbrev-ref '@{u}'`, нет → `branch not pushed yet`, это норма, пушит Step 6; (3) MR/PR уже открыт — `gh pr view --json url,state -q '.url'` либо `glab mr list --source-branch <branch>`; (4) **триггерит ли merge деплой** — есть ли в репозитории CI-джоба на push в транк (`.gitlab-ci.yml`, `.github/workflows/*`, Cloudflare Workers Builds, Vercel): да → в отчёт строка `⚠️ merge в <транк> запускает деплой <куда>`. Пользователь подтверждает результат, зная это.

Статус в отчёт: `📦 Ready to merge: <branch> → <trunk>` + строки (2)(3)(4). Репозиторий самого профиля (`~/.claude`, `~/.claude-work`) и согласованная работа в транке → `✅ N/A`, Step 6 пропускается — **кроме уборки worktree (шаг 5 Step 6): она выполняется всегда, независимо от гардов.** Скорлупы от неубранных worktree накапливались именно в профильном репозитории, потому что уборка считалась частью пропускаемого шага (замер 2026-08-31).

### 5.1.1 Auto-commit (когда коммит — единственный блокер)

Скилл вызывает `/commit` автоматически, **если все 6 условий:** (1) gate без ❌; (2) `git status --porcelain` непустой; (3) пользователь не запрещал коммит; (4) нет подозрительных файлов в diff (`.env*`/`*.key`/`*.pem`/`id_rsa*`/`*credentials*`/`*secret*`, бинарники > 1 МБ, файлы вне scope); (5) 2.8 без unbacked TODO; (6) `git rev-parse --abbrev-ref HEAD` — **не защищённая ветка** (`main`/`master`/`develop`/`release/*`, реестр `~/.claude/config/protected-branches.local.json`), кроме репозиториев самого профиля (`~/.claude`, `~/.claude-work`).

Условие (6) не выполнено → auto-commit НЕ запускать, статус `⚠️ protected branch`: правки лежат в транке, решение (перенести в ветку через `git stash` + worktree / признать согласованным hotfix) принимает пользователь через `AskUserQuestion`.

Выполнены → `Skill(skill="commit")`, перепроверить `git status`. Чисто → `✅ commit auto-created`, SHA в отчёт. Не чисто → `❌ auto-commit failed`, stderr в отчёт, передать пользователю.

**НЕ запускается:** ❌ блокер; явный отказ; подозрительные файлы (→ `AskUserQuestion`); промежуточное состояние (Partially Done, diagnostic-логи, mixed-scope diff). Полный список guard-условий, шаблоны, обработка pre-commit hook → `references/auto-commit-rules.md`.

### 5.2 Final Report

Табличка `TASK GATE` со всеми пунктами 2.0–2.10 (включая 2.2b и 2.3b) + 3 + 4 + 5.1 + статусами; первой строкой — `Mode: full | lite`, отложенные пункты — строкой `⏸ deferred to pre-merge (full) gate`, завершить `VERDICT: <READY|READY WITH WARNINGS|NOT READY>`. После — обязательно секция Recommendations (5.2.1).

**Отсечки времени (`⏱`) — замер, а не оценка.** Три числа, каждое снимается `date +%s` вокруг реального вызова; ничего не «прикидывать по ощущению» — строка, взятая с потолка, хуже отсутствующей, потому что попадёт в лог и в неё поверят:

- `gate` — от начала Step 1 до печати вердикта;
- `review` — от спавна фан-аута (2.0) до приёма последнего результата (2.9);

```

```

И одна строка в `~/.claude/stats/task-gate-timings.jsonl` (каталог `stats/` вне git, путь абсолютный — из worktree пишется туда же):

**Значения подставлять литералами**, одной командой — переменные шелла между вызовами `Bash` не сохраняются, а незаданная переменная даёт `"gate_sec":,`, то есть битую строку в логе, который и заведён ради чисел:

Маркеры: `4 Recommendations` → `✅ N queued (H/M/L)`. `5.1 Commit`: `✅` / `✅ auto` (SHA в ответ) / `⚠️ deferred` / `❌ uncommitted`.

## Step 6 — MR & Merge (после подтверждения пользователя)

Задача считается закрытой не по коммиту, а по **влитому** MR/PR (`CLAUDE.md` → «Git-коммиты»). Step 5 отдал отчёт — дальше скилл **ждёт**; сам факт `READY` merge не разрешает.

**Разрешение = подтверждение результата пользователем** после отчёта gate: «да», «готово», «мержи», «подтверждаю», «всё верно» — этого достаточно на всю цепочку, переспрашивать по шагам нельзя. Пользователь молчит, ушёл в новую задачу, попросил паузу или назвал недостаток → Step 6 не запускается, в отчёте `⚠️ merge pending confirmation`.

**Гарды (не выполнено любое → Step 6 стоп, строка в отчёт):** вердикт Step 5 — `READY` или `READY WITH WARNINGS`, ни одного `❌`; **`deferredChecks` в state-файле пуст** — долг `lite`-прогонов (2.3b, Step 3, Step 4) закрыт `full`-прогоном, иначе `⚠️ merge blocked: <N> deferred checks — прогнать full gate` (без этого ветка уезжает в merge, ни разу не увидев свежего ревьюера); текущая ветка не защищённая; `git status --porcelain` пуст (незакоммиченного нет); 2.1 Validation не `❌`; репозиторий не `~/.claude` / `~/.claude-work`; пользователь не запрещал merge в этой сессии.

**Последовательность:**

0. **Обновить базу — до push, всегда.** `git fetch origin <trunk>`; `git merge-base --is-ancestor origin/<trunk> HEAD` не проходит → влить транк в ветку (`git merge origin/<trunk>` либо rebase на неопубликованной) и **перепрогнать валидацию 2.1 на объединённом коде** — merge без текстового конфликта не значит, что оно компилируется. Красная валидация после вливания → `❌ base merge broke validation`, Step 6 стоп, push не делать. Конфликт разрешать здесь, в ветке, а не в UI GitLab/GitHub, где нет ни сборки, ни тестов; завершающий merge-коммит базы — исключение из «коммиты только через `/commit`». Пропуск шага не ловится push'ем: устаревшая база пушится успешно и вскрывается только на merge. MR транк→транк (релизный `develop → main`) — исключение: обратное вливание запрещено флоу.
1. **Push** — `git push -u origin <branch>` (апстрим уже есть → обычный `git push`).
2. **MR/PR** — открыт (5.1a) → переиспользовать. Нет → создать: GitLab `glab mr create --fill --remove-source-branch --target-branch <trunk>`, GitHub `gh pr create --fill --base <trunk>`. Заголовок и тело — из коммитов задачи; активный документ `docs/` есть → ссылка на него в теле.
3. **Merge — squash, по зелёному pipeline.** GitLab: `glab mr merge <iid> --squash --auto-merge --remove-source-branch --yes`. GitHub: `gh pr merge <num> --squash --auto --delete-branch`. Pipeline в проекте отсутствует → те же команды без `--auto-merge` / `--auto`.
4. **Дождаться результата.** Merge отложен до CI — дождаться финального состояния MR (`glab mr view <iid>` / `gh pr view <num> --json state,mergedAt`), не заявлять «влито» по факту постановки в очередь. Красный pipeline или конфликт → merge не состоялся: `❌ merge failed: <причина>`, лог в отчёт, чинить, не переоткрывать MR и не мержить в обход CI.
5. **Уборка после подтверждённого merge** — remote-ветка (снята флагом `--remove-source-branch` / `--delete-branch`, иначе `git push origin --delete <branch>`); worktree — `ExitWorktree({action: "remove"})`, он возвращает CWD в исходный каталог и сносит каталог с локальной веткой (`git worktree remove` из сессии, стоящей внутри этого каталога, не отработает). **После КАЖДОГО `ExitWorktree` — проверить каталог на диске и, если он пуст, добить `rmdir`:** на Windows тул регулярно оставляет пустую скорлупу (иногда с ответом «could not remove it — kept at …», иногда молча), git о ней уже не знает, штатной командой она не убирается и копится молча. Непустой каталог не трогать — это недоснесённый worktree с файлами; три исхода и готовая команда — `references/mr-merge.md` → «Каталог после `ExitWorktree`». Затем основной checkout на транк и `git pull`.
6. **Отчёт** — блок `🔀 Merge:` со строками `MR: <url>`, `Merged: <sha в транке>`, `Cleanup: branch/worktree removed`, `Deploy: <triggered … | none>`.

Точные команды по платформам, поведение при отсутствии `gh`/`glab`, protected-branch и approval-правилах, конфликте и красном CI, а также правила уборки worktree — [`references/mr-merge.md`](references/mr-merge.md).

## Output Style

Печатать промежуточные статусы (`✅`/`⚠️`/`❌`), не молчать на 6 шагов сразу. Не дублировать CLAUDE.md — только результаты и точные действия. Русский язык. **ОБЯЗАТЕЛЬНО** в финальном ответе блок `💡 Recommendations summary` (5.2.1) даже при нулевом списке — без него gate не прошёл.

## Что скилл НЕ делает

Не делает **глубокое** код-ревью (`/review`/`compound-engineering:ce-review`) — 2.3b это две узкие оси на диффе ветки перед мержем, не полный аудит; не делает security-аудит (`/security-review`); не вызывает `git commit` через Bash (только `/commit` или auto через 5.1.1); не мержит без подтверждения пользователя и не обходит красный CI (Step 6); не пишет документацию (проверяет `@doc-writer`); не оптимизирует субагентов (записывает рекомендации в queue, Step 4).

## Edge cases

Нестандартные ситуации (не git-репо, сессия без задачи, недописанная задача, упавший doc-writer, потерянный state-файл, фоновый task, malformed STATS_ROW, out-of-scope recommendations, auto-commit упал на pre-commit hook) → `references/edge-cases.md`.
