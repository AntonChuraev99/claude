# Task Gate — Definition of Done

Скилл-чеклист, проверяет, что завершённую задачу можно безопасно закрыть. Источник правил — Definition of Done в глобальном `~/.claude/CLAUDE.md`. Единица работы — **задача** (фича/фикс), не сессия: за сессию с несколькими задачами скилл запускается несколько раз, по разу на задачу.

## Зачем это нужно

После сложной задачи легко забыть обязательный пункт: COMPLETE документа задачи по `/doc-task`, строку в `~/.claude/stats/doc-writer.md`, строку в `docs/solutions/INDEX.md`, коммит через `/commit`. Каждый пропуск ломает compound effect. Запускай **до** финального ответа «всё готово».

**Императив (CLAUDE.md → Definition of Done):** на любой задаче, где менялся код или конфигурация, скилл **обязан** быть запущен перед финальным ответом. Без него строка статистики не пишется, INDEX не дописывается — следующая сессия не найдёт решение, `## Deferred Work` не сверяется. Вопрос-ответ и read-only анализ — без gate. Аудит 2026-05-27 (ещё под именем end-session): запускался в 14% подходящих сессий — имя «конец сессии» мешало запускам mid-session, отсюда переименование. Запуск ~10 сек, цена пропуска — недели потерянной памяти.

## Когда скилл активируется

**Триггеры:** задача завершена — «готово», «фича готова», «фикс готов», «финализируй»; конец сессии — «заканчиваем», «end session», «можно закрывать?», «wrap up»; главный агент считает задачу завершённой; после последней правки + валидации. **Не активируется:** посреди отладки/рефакторинга/открытых TODO; пользователь сказал «продолжим завтра» без просьбы зачехлить.

## Re-entrancy — несколько прогонов за сессию

Каждый прогон gate скоупится **диффом текущей задачи**, не всей сессии. Состояние между прогонами — файл `task-gate-state.json` в session-scratchpad (директория из системного промпта):

```json
{ "lastGateSha": "<HEAD на момент прошлого пройденного gate>",
  "reviewedSha": "<HEAD на момент последнего 2.3b, закрытого без ❌>",
  "onceChecks": { "hookSetup": true, "activeHygiene": true, "rollup": true },
  "artifactServer": { "taskId": "<id фоновой задачи dev-server из 5.1b>", "url": "http://localhost:3000/settings" } }
```

**BASE_SHA** для diff-скоупа (2.2 impact, 2.4 проверка фактов, 2.6 `Шагов: N`, 2.8 TODO-scan, L1 в 2.0) — первый доступный: (1) `lastGateSha` из state-файла; (2) START_SHA начала сессии, если известен; (3) нет ни того ни другого → рабочее дерево без `--base`.

**После пройденного gate** (вердикт READY / READY WITH WARNINGS, включая auto-commit): записать `lastGateSha = HEAD` в state-файл. **Once-per-session проверки** (помечены `[once]` ниже) — только в `full`, на повторном прогоне скипаются со статусом `✅ once (done earlier)`: hook setup (2.9), active hygiene (2.4), rollup `stats.py` (2.9).

**`reviewedSha`** — граница уже отревьюенного (2.3b). Пишется на **любом** прогоне, когда ревью закрылось без `❌` (с 2026-09-15 ревью идёт в обоих режимах). Даёт инкрементальный скоуп повторным прогонам одной ветки: третий прогон ревьюит приращение, а не ветку заново. Поле `deferredChecks` упразднено: 2.3b больше не откладывается, а Step 3 и Step 4 в `lite` **пропускаются**, не переносятся.

## Workflow

5 шагов **последовательно**, статус (`✅`/`⚠️`/`❌`) после каждой проверки, финальный отчёт в конце: Step 1 — Task Snapshot (+ выбор режима); Step 2 — Definition of Done Checks; Step 3 — Sub-agent Sanity Check; Step 4 — Recommendations Pull; Step 5 — Commit & Final Report.

**Исключение из последовательности — 2.0 Review fan-out:** ревью-агенты запускаются фоном первым делом в Step 2 и работают, пока идут 2.1–2.8; их результаты принимаются в 2.3b и 2.9. Всё остальное по-прежнему по порядку.

**Гейт двухрежимный, `lite` — дефолт** (2026-08-19, перевёрнуто 2026-09-15): `lite` — проверки, которые ловят баги, плюс один ревьюер диффа; `full` добавляет бухгалтерию. Режим выбирается в Step 1, печатается в snapshot и в финальном отчёте. Дальше скилл **останавливается и ждёт подтверждения пользователя**; получено → Step 6 — MR & Merge (обновление базы, push, MR/PR, merge, уборка).

## Step 1 — Task Snapshot

Собрать: BASE_SHA (см. Re-entrancy) и изменённые файлы задачи (`git status` + `git diff --stat <BASE_SHA>`); вызванные специалисты; путь к активному документу в `docs/active/` (может отсутствовать — документ создаётся не на каждую задачу).

Печатать `📋 Task snapshot:` + строки `Base`, `Files changed`, `Agents used`, `Active doc`, `Mode`. Повторный прогон за сессию → добавить строку `Gate run: #N in session`.

### 1.1 Режим гейта — `lite` (дефолт) или `full`

**`full`** — если верно **хотя бы одно**: дифф ≥ 5 файлов · появился новый модуль, миграция или новый публичный контракт (API, схема, событие аналитики) · тронут деплой, инфраструктура или конфигурация окружения · дифф трогает `~/.claude/{CLAUDE.md,agents,skills,settings.json,rules,review-rules}` · пользователь попросил полный прогон. **«Последний прогон перед мержем» режим НЕ поднимает** — с этим триггером `full` был в 39 гейтах из 40, а `lite` не существовал на практике (прецедент task-gate-lite-default в `references/claude-md-precedents.md`).

**`lite`** — всё остальное, и это дефолт.

**Что гоняет `lite`:** 2.0 review fan-out — **один** ревьюер 2.3b (обе оси одним вызовом, бюджет 25 вызовов) + L1 + L2 по его триггеру · 2.1 validation · 2.2 impact scan · 2.2b скриншот-цикл (если дифф трогал вёрстку — правило не ослабляется режимом) · 2.3 self-check · 2.3b приём ревью и триаж · 2.4, 2.5, 2.7, 2.7b — только если задача набрала признак документирования (иначе `✅ N/A`), без `[once]`-подпунктов · 2.8 deferred work · 2.9 — L1 static, L2 по триггеру, L3 process; без rollup и hook-setup · 2.10 improvements log (его триггер и так форсит `full`, в `lite` — `✅ N/A`) · Step 5 commit, 5.1a, 5.1b артефакт, короткий отчёт 5.2 без `⏱`-замеров и без 5.2.1, но **со строкой в `task-gate-timings.jsonl`** (`mode:"lite"`, длительности `null` — по этому файлу меряются improvements 2026-08-26 / 08-31 / 09-14, и `lite` как дефолт не должен их ослепить).

**Что `lite` пропускает** (строкой `⏸ lite` в отчёте, **не переносится**): 2.6 строка статистики · Step 3 sub-agent sanity · Step 4 recommendations pull (рекомендации остаются в секции документа задачи, если он писался) · `[once]`-проверки 2.4/2.9 · `⏱`-снимки `date +%s` и строка `⏱ Timings` в отчёте · блок 5.2.1.

**Что режим НЕ ослабляет ни при каких условиях:** 2.2b (вёрстка проверяется картинкой), 2.3b (один ревьюер — в любом режиме), 2.8 (отложенный функционал), 2.9 static-HIGH как блокер, 5.1b (артефакт для подтверждения), запрет коммитить мимо `/commit`.

## Step 2 — Definition of Done Checks

9 пунктов CLAUDE.md → «Definition of Done» + п. 2.3b (diff review двумя осями) + п. 2.9 (bug-pattern review). Прогоняй по порядку, статус одной строкой — **кроме 2.0: он стартует первым и работает фоном под остальными пунктами.**

### 2.0 Review fan-out (старт ревью — до остальных проверок)

Ревью-агенты — самая долгая часть гейта, а их находки нужны только к финальному отчёту. Поэтому они стартуют **первыми и фоном**, а 2.1–2.8 идут, пока они работают; результаты принимаются на своих местах — в 2.3b и 2.9. Раньше 2.3b и 2.9 стояли по порядку шагов и складывались во времени, хотя между ними нет зависимости: линзы разные, выходы разные.

1. **Контекст-пакет — один раз на все оси.** `references/diff-review-axes.md` → «Контекст-пакет»: главный собирает дифф в `<session-scratchpad>/review-package-<sha>.md` и раздаёт агентам **путь**, не содержимое. **База пакета — по правилу 2.3b, и алгоритм её выбора лежит в [`references/diff-review-flow.md`](references/diff-review-flow.md) → «База ревью»: прочитать его ЗДЕСЬ, до сборки пакета**, иначе пакет соберётся по диффу задачи вместо `reviewedSha` / `origin/<транк>`, и ревьюеры увидят меньше ветки, чем должны.

   **Пакет собирается по базе 2.3b, и его диапазон записан в шапке.** У L2 база своя (`BASE_SHA`), и совпадают они не всегда: `reviewedSha` двигает базу 2.3b вперёд независимо от `lastGateSha`. Базы разошлись → **собрать L2 второй пакет** той же командой от его базы, отдельным файлом. Это ещё один `git diff` главного — но он всё равно дешевле, чем холодный сбор внутри агента, и сохраняет выигрыш (a) на всём фан-ауте, а не на двух третях. Чего делать нельзя — отдать L2 пакет чужого диапазона: агент примет его за свой скоуп и отревьюит не то, о чём отчитается.
2. **L1 static — до фан-аута, один прогон на гейт.** Вывод сразу в файл рядом с пакетом:

   ```bash
   python ~/.claude/review-rules/run.py --base <BASE_SHA> --changed-only --json \
     --log ~/.claude/stats/review-rules-events.jsonl --entry endsession \
     > <session-scratchpad>/l1-<short-sha>.json
   ```

   Детерминированно, без LLM, секунды; `--entry endsession` — исторический лейбл, не менять. Гонится здесь, потому что его вывод — триггер L2; путь к этому JSON идёт в бриф L2, агент его читает, а не перезапускает. Разбор находок и статусы — 2.9, второй раз команду не запускать.
3. **Фан-аут — все вызовы `Agent` одним сообщением.** У `Agent` **нет** параметра `run_in_background` (он есть у `Bash`): вызов и так возвращается сразу, результат приходит уведомлением. «Фоном» здесь означает ровно одно — **отправить все вызовы одним сообщением и идти дальше в 2.1**, не дожидаясь ответов.
   - **Оси 2.3b — по умолчанию ОДИН вызов** `Agent(subagent_type="general-purpose")` с обеими осями в брифе и раздельными секциями в ответе; модель **не** понижать, бриф несёт Spec-ось. Два отдельных вызова — только по порогу 2.3b (дифф >30 файлов либо трогает деньги, безопасность, деплой): тогда Standards получает `model="sonnet"` (аудит по готовому чеклисту — прецедент improvements 2026-06-01: «opus редко даёт прирост на research/audit»), Spec — модель сессионную, на нём не экономим.
   - **L2** — `Agent(subagent_type="bug-pattern-reviewer")`, **только если L1 дал находку в режиме `static`** (триггер сужен, см. 2.9). Модель у него своя, во frontmatter.
   - **Бюджет вызовов — в бриф каждой оси ДО отправки** (дописать здесь, а не после: отправленный бриф не поправить): строка «не больше 25 вызовов инструментов, отчёт обязателен, непрочитанное — строкой `не просмотрено:`». Модель исполняет её буквально и возвращает частичный отчёт вместо зависания. Прецедент 2026-09-14: Spec-ось без бюджета 74 минуты «running», пользователь спросил «что так долго»; респавн с бюджетом вернулся за 5,5 мин.
   Итого типичный фан-аут — **два вызова** (оси + L2), а не три; при чистом `static` — один.
4. **Сторож — сразу после фан-аута, одной фоновой командой.** `ListAgents` показывает «running» и у зависшего агента, а встроенные типы (`general-purpose`, оси 2.3b) транскрипт `output_file` не пишут вовсе (0 байт у живого и у зависшего одинаково) — для них работает только потолок по времени: `WATCHDOG_ZERO_SEC=0 WATCHDOG_MAX_SEC=900 sh ~/.claude/scripts/agent-watchdog.sh <output_file…>` через `Bash(run_in_background)`; `output_file` берётся из ответа `Agent`. Её `CAP` → `SendMessage` «заверши сейчас тем, что есть», ещё один сторож на 180 с, затем `TaskStop` и ось в `⚠️ diff review incomplete`. Для L2 (`@bug-pattern-reviewer` — доменный агент, транскрипт пишет) сторож с дефолтами: `STALLED-ZERO` → `TaskStop` + **один** респавн, `STALLED` → как `CAP`. `GONE` завершает сторож по одному файлу — остальные остались без наблюдения, перезапустить на них. Все агенты вернулись раньше — `TaskStop` сторожа, иначе он доживёт до потолка и скажет `CAP`.
5. **Отсечки времени — только в `full`:** три снимка `date +%s`, каждый вокруг своего вызова — в самом начале Step 1 (для `gate`), вокруг `run.py` в п. 2 (для `l1`), перед этим фан-аутом и при приёме последнего результата в 2.9 (для `review`). Числа держать в тексте прогона и подставить в 5.2 **литералами**: переменные шелла между вызовами `Bash` не переживают. В `lite` снимков нет — длительность гейта меряется снаружи по JSONL сессии (скрипт замера 2026-09-15), а не тремя лишними вызовами внутри.

**Режим `lite`** → фан-аут тот же по составу (один ревьюер 2.3b + L2 по триггеру `static`-находки), второй ревьюер по порогу 2.3b не поднимается никогда. Пакет — один, по базе 2.3b.

**Fail fast гасит только ось 2.3b, не L2.** Его условия (резолвится ли база 2.3b, непустой дифф) принадлежат 2.3b: провал любого — ревьюер не спавнится, причина печатается в 2.3b. **L2 живёт по своему триггеру — находке L1 в режиме `static` — и режимом гейта не снимается** (инвариант `CLAUDE.md` → «Bug-pattern gate»): нерезолвящийся `origin/<транк>` его не отменяет.

**Ревью-агенты read-only.** Агент не наследует PreToolUse-хуки главного, поэтому запрет на запись держится только брифом — строка «ничего не редактируй, не коммить, не запускай сборки и тесты; твой продукт — отчёт» обязательна в каждом. У `@bug-pattern-reviewer` есть ещё и ограничение инструментов, но **на него не полагаться**: frontmatter объявляет `Read, Grep, Glob, Bash`, а рантайм-реестр агентов показывает у него дополнительно `Write, Edit` — расхождение не в пользу запрета.

Статус: `✅ N agents dispatched (<оси>)` / `⚠️ not dispatched (<причина>)`.

### 2.1 Validation

Сборка/тесты прошли. Не была сборка → `⚠️ unverified` + рекомендация запустить. Тесты — аналогично.

### 2.2 Impact Scan

Все зависимости обновлены: импорты, использования, тесты. Проверять через `ast-index` по именам ключевых сущностей, изменённых **в этой задаче** (дифф от BASE_SHA): `ast-index changed --base <BASE_SHA>` даёт список изменённых символов, дальше `usages` / `refs` / `implementations` по каждому. `Grep` — fallback на regex, строковые литералы и файлы вне индекса; `rebuild`/`update` не запускать. Правка в одном файле без новых или переименованных символов — отметить, что сканировать нечего.

### 2.2b Скриншот-цикл (только если дифф трогал вёрстку)

Дифф содержит UI-файлы (Compose-composable, `.tsx`-компоненты, стили) → в отчёте **таблица по поверхностям**, а не общий вердикт по задаче: строка на каждый экран или компонент, который задача изменила **либо впервые сделала достижимым**; в строке — путь к кадру, который агент открывал, и что на нём видно, либо `не снят` + причина. **Кадры соседней поверхности чужую строку не закрывают.** Инвариант CLAUDE.md → «Вёрстка — проверяется картинкой, а не пользователем», процедура — скилл `screenshot-driven-ui`.

Секция сработала → **прочитать [`references/screenshot-gate.md`](references/screenshot-gate.md) целиком** до заполнения таблицы: проверка инфраструктуры по МОДУЛЮ изменённого файла (а не по репозиторию, со снипетом обхода Compose-модулей и правилом для web-диффа), правило «впервые достижимая поверхность идёт в таблицу, даже если её код не менялся», прецедент 2026-08-17.

### 2.3b Diff review свежим агентом (Standards + Spec)

Инвариант CLAUDE.md → «Роль главного агента»: **единственное** ревью диффа на задачу — здесь. Свежий субагент видит только дифф и критерий, не видит рассуждений, которые к нему привели. Отдельного «fresh diff review» до гейта больше нет (2026-09-15: два ревью одного диффа — 132 ревьюера за неделю, 2.2 на гейт). Метод — две независимые оси (скилл `code-review`):

- **Standards** — соответствует ли код документированным правилам проекта + smell baseline (12 смелов Фаулера).
- **Spec** — реализует ли дифф то, о чём просили (активный документ задачи / Prompt Contract): пропущенные требования, scope creep, неверно понятые требования.

**Когда запускать — в любом режиме, при одном условии:**

1. **Дифф непуст** относительно базы ревью (`reviewedSha` → `origin/<транк>` → `BASE_SHA`). Повторный гейт той же ветки ревьюит только приращение. Наличие исполняемого кода определяет не «запускать или нет», а **сколько агентов** (в `lite` — всегда один):

   - **Код есть** → smell baseline применяется. Считается кодом: исходники (`.kt .kts .java .swift .ts .tsx .js .jsx .py .rb .go .rs .php .sql .sh .ps1`), build-скрипты (`*.gradle`, `*.gradle.kts`, `Podfile`, `package.json` в части скриптов и зависимостей) и **конфигурация, исполняемая внешней системой** (`.github/workflows/**`, `.gitlab-ci.yml`, `wrangler.*`, `firebase.json`, `*.tf`, правила безопасности БД). Число агентов при этом определяет порог ниже, а не сам факт кода: дефолт — один.
   - **Кода нет** — правила самого харнесса (`~/.claude/**`), `docs/**`, любые `.md`, `review-rules/*.yaml`, локализация, статические ассеты → один агент при любом размере диффа. Standards на таком диффе = сверка с документированными правилами (`CLAUDE.md` и его инварианты, конвенции репозитория) плюс целостность ссылок на скиллы, агентов и файлы; **smell baseline Фаулера не применять** — он про код. Spec — без изменений, это единственный механизм, ловящий «сделано не то, о чём просили».

   Решение 2026-08-19 после того, как ревью диффа правил (два агента) нашло в нём три блокера уровня high: правки инвариантов без внешнего взгляда не отгружаются, но платятся одним холодным контекстом, а не двумя.

`/code-review` уже прогонялся по этой задаче → `✅ verified by /code-review`.

**Механика прогона — [`references/diff-review-flow.md`](references/diff-review-flow.md), прочитать ДО спавна ревьюеров.** Там: выбор базы (`reviewedSha` → `origin/<транк>` → `BASE_SHA`) и диапазон до рабочего дерева, а не до HEAD · сверка отпечатка диффа перед записью `reviewedSha` и правило «двигается только на успехе» · число агентов и порог второго (только `full`) · строка convergence на повторном прогоне · приём отчётов раздельно по осям · **обязательный триаж `failure_scenario` перед починкой** · починка одним агентом пачкой · поведение при не вернувшейся оси.

Полные промпты, smell baseline, порядок поиска Spec-источника, правила «проект перекрывает baseline» и «пропускать то, что ловит линтер» → [`references/diff-review-axes.md`](references/diff-review-axes.md).

Статус: `✅ clean (2 axes, 1 reviewer)` / `✅ clean (2 axes, 2 reviewers — <причина порога>)` / `⚠️ N standards + M spec findings (+K triaged out, optional: L)` / `❌ spec: требование не реализовано` (блокер — задача не делает того, о чём просили). Standards-находки уровня суждения gate не блокируют; их место — в отчёт.

### 2.4 Документ задачи — `/doc-task` COMPLETE + проверка фактов

Документ задачи и постоянный документ пишет **главный** по скиллу `doc-task` (субагент `doc-writer` распущен 2026-09-15: писатель без контекста задачи выдумывал факты — 19 переписанных документов за месяц). Gate проверяет, что COMPLETE пройден и факты сверены машиной.

**Критерий обязательности** (`~/.claude/CLAUDE.md` → «Документирование»). Документ обязателен, если задача набрала **хотя бы один** признак — проверяются по факту диффа и хода работы, не по предварительной оценке:

- понадобилось 2+ итерации либо начальный план оказался неверен;
- тронуто 5+ файлов, появился новый модуль или выполнена миграция;
- recurring bug либо исправление, влияющее на всё приложение (перф, архитектура, security);
- инфраструктурный фикс с нетривиальной причиной (CSP, конфиг Firebase, DI, регионы, сериализация);
- пользователь попросил задокументировать.

Ни одного признака → `✅ skipped (rule)`.

**Признак есть → пройти COMPLETE по `doc-task`** (`## Выводы`, постоянный документ при переиспользуемом знании, строка INDEX, архивация при `Done`). Стаба в `docs/active/` нет — реконструировать из диффа, в шапку `⚠ INIT пропущен`. Входы: **`Шагов: N`** (правила подсчёта — `references/calibration.md`; шаги **этой задачи** от BASE_SHA, не всей сессии) и `git diff --name-only <BASE_SHA> -- ':(exclude)docs/*'`.

**Проверка фактов — обязательна, до Step 5:**

```
node ~/.claude/hooks/docs-facts-guard.js <все файлы из DOCS_WRITTEN и ARCHIVED> --base <BASE_SHA>
```

`LINK` > 0 → `❌ docs facts: <n> broken links` — блокер, маркером не закрывается: относительная ссылка либо резолвится, либо правится. `PATH` > 0 → `❌ docs facts: <n> missing paths` — правка; путь вне репозитория (gitignored, чужой репо) закрывается `(не проверено — <почему>)` в той же строке. `IDENT` или `NUMBER` > 0 → `⚠️ docs facts: <n> unverified` с перечнем в отчёт; каждую закрыть до коммита (правка по файлу, `TODO: сверить с <файл>`, `источник:` в строке, `(приблизительно)`, `(не проверено — <почему>)`). С `--base` скрипт отчитывает только претензии, которых не было в версии документа на базе задачи — правка абзаца в старом документе не делает задачу ответственной за его прошлогодние ссылки (`--all` — полный аудит по запросу). Хук делает ту же проверку на каждой `Write`/`Edit` в `docs/{solutions,decisions,archive}/`; прогон в gate — контрольный, по документу после `mv` в архив, которого хук не видит. Чисто → `✅ docs facts clean`.

**Active hygiene `[once]` (анти-свалка `docs/active/`, только `full`).** Раз за сессию, на первом `full`-прогоне gate. Быстрый scan: (а) файлы со `**Статус:** Done` в шапке, всё ещё лежащие в `docs/active/` → доархивируй `mv docs/active/<f> docs/archive/<f>`; (б) файлы с `In Progress` в шапке, но заполненными `## Выводы` / `Done` в теле → выровняй шапку на `**Статус:** Done` и перенеси в `docs/archive/`. Ловит COMPLETE прошлых сессий, не довёдшие Шаг 7. Документ остаётся в `docs/active/` только при `In Progress` / `Partially Done` / `Deferred` / `Planned`. ### 2.9 Bug-pattern review (L1 static + L2 reviewer + L3 process gate)

Сверка diff с реестром повторяющихся багов `~/.claude/review-rules/` — система против «тех же багов каждую сессию» (system bar не покрашен, анимация, отступы, регион деплоя, субагент выпилил фичу). Источник — `~/.claude/review-rules/README.md`.

- **L1 (всегда, дёшево, без LLM):** Stop-хук уже прогнал L1 по ходу сессии и залогировал. - **L3 process-gate (всегда, дёшево):** пройти armed process-вопросы (из L2 либо прочитать `process-gate.yaml` сам): молча ли удалена user-facing функция? тронут деплой → регион/аккаунт/smoke сверены? субагент в scope, не коммитил? баг невоспроизведён, а патчишь? Любой неотвеченный armed-вопрос severity high → `⚠️` в отчёт (боль #5 — не отгружать молчком; при потере функции — `AskUserQuestion` ДО завершения).
- **Компаундинг (опц.):** L2 вернул NEW_RULE_CANDIDATE для recurring-бага без правила → допиши строку в нужный area-файл (README → «Компаундинг»). Не блокирует.

### 5.1b Артефакт для подтверждения (ОБЯЗАТЕЛЬНЫЙ, режимом не снимается)

Пользователь подтверждает результат по отчёту — значит, в отчёте лежит то, что он может открыть и потрогать, а не таблица статусов и дифф. Класс артефакта — по платформе диффа, приоритет фиксирован:

- **Web** (React/Next.js, wasmJs, любой браузерный) → **живой `http://localhost:<port>/<путь до экрана>`**: dev-server поднят скиллом `run` из worktree задачи (`run_in_background`), ответ проверен (`curl -sI` / Playwright), **живёт до подтверждения** — гасит Step 6 п. 5. Id задачи и URL — в `artifactServer` state-файла; **повторный прогон gate** → старый сервер остановить (`TaskStop`) и поднять заново, чтобы localhost отдавал код после фикса; занятый порт — fallback только когда процесс чужой. PNG — дополнение к URL, не замена.
- **Android** → **debug APK под физическое устройство пользователя**: `./gradlew :<module>:assembleDebug` (модуль — по `com.android.application`, алгоритм в `commands/install-device.md`), путь к APK + `adb devices -l` → `MODEL (SERIAL)`. **Установка — только с ведома пользователя, и согласие относится к сборке после последней правки кода:** согласие = он попросил поставить результат **после** последней правки, либо ответил на `AskUserQuestion` после отчёта («Установить на <MODEL> сейчас (Recommended)» / «Сам поставлю» / «Не нужно»); просьба или `/install-device` до правки (репро бага на старой сборке) на новую сборку не переносится. Без ответа `adb install`, `installDebug`, `/install-device` не вызывать; согласие есть → `/install-device` (ответ на вопрос для него — явный запуск).
- **Остальное** (CLI, backend, скрипт, конфиг, доки, харнесс) → то, что показывает результат: вывод команды или теста, `curl` на endpoint, лог, PNG, путь + ключевой фрагмент, страница `Artifact`.

Несколько платформ в одном диффе → артефакт на каждую. Первый приоритет недостижим → fallback следующего класса **с причиной, доказанной выводом команды** (`⚠️ fallback: <вид> — <причина>`). Артефакта нет вовсе → `❌ no artifact`, вердикт `NOT READY`. Процедура по платформам, что артефактом не считается, формат строк — [`references/artifact-handoff.md`](references/artifact-handoff.md), прочитать до сборки артефакта.

Статус: `✅ localhost <url>` / `✅ APK <путь>; установка: <по согласию | ждёт ответа | не запрошена>` / `✅ <вид>: <путь | вывод>` / `⚠️ fallback: …` / `❌ no artifact`.

### 5.1.1 Auto-commit (когда коммит — единственный блокер)

Скилл вызывает `/commit` автоматически, **если все 6 условий:** (1) gate без ❌; (2) `git status --porcelain` непустой; (3) пользователь не запрещал коммит; (4) нет подозрительных файлов в diff (`.env*`/`*.key`/`*.pem`/`id_rsa*`/`*credentials*`/`*secret*`, бинарники > 1 МБ, файлы вне scope); (5) 2.8 без unbacked TODO; (6) `git rev-parse --abbrev-ref HEAD` — **не защищённая ветка** (`main`/`master`/`develop`/`release/*`, реестр `~/.claude/config/protected-branches.local.json`), кроме репозиториев самого профиля (`~/.claude`, `~/.claude-work`).

Условие (6) не выполнено → auto-commit НЕ запускать, статус `⚠️ protected branch`: правки лежат в транке, решение (перенести в ветку через `git stash` + worktree / признать согласованным hotfix) принимает пользователь через `AskUserQuestion`.

Выполнены → `Skill(skill="commit")`, перепроверить `git status`. Чисто → `✅ commit auto-created`, SHA в отчёт. Не чисто → `❌ auto-commit failed`, stderr в отчёт, передать пользователю.

**НЕ запускается:** ❌ блокер; явный отказ; подозрительные файлы (→ `AskUserQuestion`); промежуточное состояние (Partially Done, diagnostic-логи, mixed-scope diff). Полный список guard-условий, шаблоны, обработка pre-commit hook → `references/auto-commit-rules.md`.

## Step 6 — MR & Merge (после подтверждения пользователя)

Задача считается закрытой не по коммиту, а по **влитому** MR/PR (`CLAUDE.md` → «Git-коммиты»). Step 5 отдал отчёт — дальше скилл **ждёт**; сам факт `READY` merge не разрешает.

**Разрешение = подтверждение результата пользователем** после отчёта gate: «да», «готово», «мержи», «подтверждаю», «всё верно» — этого достаточно на всю цепочку, переспрашивать по шагам нельзя. Пользователь молчит, ушёл в новую задачу, попросил паузу или назвал недостаток → Step 6 не запускается, в отчёте `⚠️ merge pending confirmation`.

**Гарды (не выполнено любое → Step 6 стоп, строка в отчёт):** вердикт Step 5 — `READY` или `READY WITH WARNINGS`, ни одного `❌`; текущая ветка не защищённая; `git status --porcelain` пуст (незакоммиченного нет); 2.1 Validation не `❌`; репозиторий не `~/.claude` / `~/.claude-work`; пользователь не запрещал merge в этой сессии.

**Не гард:** `⚠️ diff review incomplete` (ревьюер 2.3b не вернулся, `references/diff-review-flow.md` → «Ось не вернулась»). Строка стоит в отчёте, по которому пользователь подтверждает результат; подтвердил — Step 6 идёт, `reviewedSha` при этом не двигается, и следующий прогон ветки ревьюит тот же диапазон.

**Последовательность:**

0. **Обновить базу — до push, всегда.** `git fetch origin <trunk>`; `git merge-base --is-ancestor origin/<trunk> HEAD` не проходит → влить транк в ветку (`git merge origin/<trunk>` либо rebase на неопубликованной) и **перепрогнать валидацию 2.1 на объединённом коде** — merge без текстового конфликта не значит, что оно компилируется. Красная валидация после вливания → `❌ base merge broke validation`, Step 6 стоп, push не делать. Конфликт разрешать здесь, в ветке, а не в UI GitLab/GitHub, где нет ни сборки, ни тестов; завершающий merge-коммит базы — исключение из «коммиты только через `/commit`». Пропуск шага не ловится push'ем: устаревшая база пушится успешно и вскрывается только на merge. MR транк→транк (релизный `develop → main`) — исключение: обратное вливание запрещено флоу.
1. **Push** — `git push -u origin <branch>` (апстрим уже есть → обычный `git push`).
2. **MR/PR** — открыт (5.1a) → переиспользовать. Нет → создать: GitLab `glab mr create --fill --remove-source-branch --target-branch <trunk>`, GitHub `gh pr create --fill --base <trunk>`. Заголовок и тело — из коммитов задачи; активный документ `docs/` есть → ссылка на него в теле.
3. **Merge — squash, по зелёному pipeline.** GitLab: `glab mr merge <iid> --squash --auto-merge --remove-source-branch --yes`. GitHub: `gh pr merge <num> --squash --auto --delete-branch`. Pipeline в проекте отсутствует → те же команды без `--auto-merge` / `--auto`.
4. **Дождаться результата.** Merge отложен до CI — дождаться финального состояния MR (`glab mr view <iid>` / `gh pr view <num> --json state,mergedAt`), не заявлять «влито» по факту постановки в очередь. Красный pipeline или конфликт → merge не состоялся: `❌ merge failed: <причина>`, лог в отчёт, чинить, не переоткрывать MR и не мержить в обход CI.
5. **Уборка после подтверждённого merge** — фоновый dev-server из 5.1b остановить (`TaskStop` по id фоновой задачи) **до** `ExitWorktree`, иначе процесс держит каталог; remote-ветка (снята флагом `--remove-source-branch` / `--delete-branch`, иначе `git push origin --delete <branch>`); worktree — `ExitWorktree({action: "remove"})`, он возвращает CWD в исходный каталог и сносит каталог с локальной веткой (`git worktree remove` из сессии, стоящей внутри этого каталога, не отработает). **После КАЖДОГО `ExitWorktree` — проверить каталог на диске и, если он пуст, добить `rmdir`:** на Windows тул регулярно оставляет пустую скорлупу (иногда с ответом «could not remove it — kept at …», иногда молча), git о ней уже не знает, штатной командой она не убирается и копится молча. Непустой каталог не трогать — это недоснесённый worktree с файлами; три исхода и готовая команда — `references/mr-merge.md` → «Каталог после `ExitWorktree`». Затем основной checkout на транк и `git pull`.
6. **Отчёт** — блок `🔀 Merge:` со строками `MR: <url>`, `Merged: <sha в транке>`, `Cleanup: branch/worktree removed`, `Deploy: <triggered … | none>`.

Точные команды по платформам, поведение при отсутствии `gh`/`glab`, protected-branch и approval-правилах, конфликте и красном CI, а также правила уборки worktree — [`references/mr-merge.md`](references/mr-merge.md).

## Output Style

Печатать промежуточные статусы (`✅`/`⚠️`/`❌`), не молчать на 6 шагов сразу. Не дублировать CLAUDE.md — только результаты и точные действия. Русский язык. **ОБЯЗАТЕЛЬНО** в финальном ответе блок `💡 Recommendations summary` (5.2.1) даже при нулевом списке — без него gate не прошёл.

## Что скилл НЕ делает

Не делает **глубокое** код-ревью (полный проход `/code-review` по произвольной базе) — 2.3b это две узкие оси на диффе ветки перед мержем, не полный аудит; не делает security-аудит (`/security-review`); не вызывает `git commit` через Bash (только `/commit` или auto через 5.1.1); не мержит без подтверждения пользователя и не обходит красный CI (Step 6); документацию пишет главный по `/doc-task` — gate сверяет её факты (2.4), а не пишет; не оптимизирует субагентов (записывает рекомендации в queue, Step 4).

## Edge cases

Нестандартные ситуации (не git-репо, сессия без задачи, недописанная задача, потерянный state-файл, фоновый task, out-of-scope recommendations, auto-commit упал на pre-commit hook) → `references/edge-cases.md`.

## Связанные скиллы и файлы

- `/commit` — единственно допустимый способ создавать коммиты.
- `~/.claude/CLAUDE.md` — источник истины Definition of Done.
- `~/.claude/stats/doc-writer.md` — журнал задач (строка 2.6; имя файла историческое).
- `docs/solutions/INDEX.md` — per-project индекс (2.7).
- `doc-task` — скилл документа задачи (стаб / итерация / COMPLETE); `~/.claude/hooks/docs-facts-guard.js` — проверка фактов (2.4).
- `code-review` — скилл-источник метода двух осей (2.3b); отдельно от gate применим к произвольной базовой точке.
- `run` — запуск dev-server для localhost-артефакта (5.1b); `/install-device` — установка APK на физическое устройство, только после согласия пользователя.
- `references/` — calibration, deferred-work-scan, auto-commit-rules, mr-merge, edge-cases, diff-review-axes, artifact-handoff.
