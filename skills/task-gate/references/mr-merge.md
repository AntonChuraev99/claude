# MR & Merge — Step 6

Extract из Step 6 `task-gate/SKILL.md`. Точные команды, гарды и обработка отказов для доведения задачи до **влитого** MR/PR.

## Принцип

Задача закрыта не коммитом и не открытым MR, а изменением в транке (`CLAUDE.md` → «Git-коммиты», «Защищённая ветка и worktree»). Пользователь подтверждает результат один раз — по отчёту gate; дальше вся цепочка push → MR → merge → уборка идёт без дополнительных вопросов. Спрашивать разрешение на каждый шаг — это возврат ручного режима, ради ухода от которого правило и вводилось.

## Разрешение

**Считается подтверждением:** «да», «готово», «подтверждаю», «мержи», «всё верно», «ок, вливай» — сказанные **после** отчёта gate, в ответ на строку `Подтверди результат — дальше сам: push → MR → merge…`.

**НЕ считается:** молчание; «спасибо»; переход к новой задаче; «посмотрю позже»; подтверждение, сказанное ДО прогона gate («да делай» в начале задачи); подтверждение отдельного шага («да, закоммить») — оно закрывает только этот шаг.

**Отзывается** любой репликой про недостаток («а вот тут поправь», «стоп», «не мержи»). Отозвано → Step 6 не запускается до нового подтверждения по новому отчёту gate.

## Гард-условия (ВСЕ одновременно)

| # | Условие | Проверка |
|---|---|---|
| 1 | Вердикт Step 5 — `READY` / `READY WITH WARNINGS`, ни одного `❌` | результат Step 5 |
| 2 | Ветка не защищённая | `git rev-parse --abbrev-ref HEAD` + реестр `~/.claude/config/protected-branches.local.json` |
| 3 | Рабочее дерево чистое | `git status --porcelain` пусто |
| 4 | Validation (2.1) не `❌` | билд/тесты не падали |
| 5 | Репозиторий не профильный | не `~/.claude`, не `~/.claude-work` |
| 6 | Пользователь не запрещал merge в этой сессии | «MR сделаю сам», «пока не вливай» |
| 7 | Есть подтверждение | см. выше |

Не выполнено любое → Step 6 стоп, строка в отчёт с причиной. Гард 2 или 3 — это ещё и сигнал, что задача велась мимо worktree-правила; чинится до merge, а не после.

**Исключение из «Step 6 стоп» — уборка worktree (шаг 5).** Гарды останавливают push, MR и merge; каталог worktree убирается в любом случае, если сессия его заводила. Гард 5 (профильный репозиторий) здесь особенно важен: обе скорлупы замера 2026-08-31 накопились именно в `~/.claude`, где Step 6 штатно не запускается.

## Деплой-предупреждение

Merge в транк на проекте с CI-деплоем = выкатка пользователям. Признаки, которые проверяются в 5.1a:

- `.gitlab-ci.yml` — job с `only`/`rules` на транк и стадией deploy/publish;
- `.github/workflows/*.yml` — `on: push: branches: [<trunk>]`;
- `wrangler.jsonc` / `wrangler.toml` + Cloudflare Workers Builds на транке;
- Vercel/Netlify production branch = транк.

Нашлось → строка `⚠️ merge в <транк> запускает деплой <куда>` печатается **в отчёте gate**, до подтверждения. Пользователь подтверждает, уже зная это. Молча влить деплоящийся транк нельзя — это класс «деплой без сверки» из L3 process-gate.

Сверка аккаунта деплоя (`credentials-guard`, `~/.claude/config/project-credentials.local.md`) остаётся обязательной там, где деплой запускается локально; merge отдаёт выкатку CI, но расхождение аккаунта в CI-переменных агент не видит — если проект в реестре, назвать это в той же строке.

## Команды

Платформа определяется по `git remote get-url origin`: `gitlab` → glab, `github` → gh.

### Обновление базы (ПЕРЕД push, обязательный шаг)

Ветка ответвлялась от транка в НАЧАЛЕ задачи; к моменту MR транк почти всегда ушёл вперёд. Подтягивать его надо здесь, а не полагаться на то, что база свежая.

```bash
git fetch origin <trunk> || { echo "FETCH FAILED"; exit 1; }   # упавший fetch НЕ трактовать как «база свежая»
git merge-base --is-ancestor origin/<trunk> HEAD; case $? in
  0) echo UP-TO-DATE ;;
  1) echo BEHIND ;;
  *) echo "CHECK FAILED — битый ref, разбираться, а не пушить" ;;
esac
# BEHIND → влить транк в ветку и ПЕРЕПРОГНАТЬ валидацию (2.1) на объединённом коде
git merge origin/<trunk> --no-edit     # либо git rebase origin/<trunk> на неопубликованной ветке
```

`&& echo UP-TO-DATE || echo BEHIND` здесь не годится: `--is-ancestor` отдаёт 1 на «не предок» и >1 на ошибку, и однострочник отрапортует BEHIND на упавшем fetch — то есть на битом ref'е агент пойдёт «вливать транк», которого нет.

Конфликт — разрешать здесь, в своей ветке, где есть контекст задачи и можно прогнать сборку. Разрешение конфликта в UI GitLab/GitHub запрещено: там нет ни билда, ни тестов, а результат уезжает в транк непроверенным. Завершающий merge-коммит базы делается `git commit` напрямую — это единственное исключение из правила «коммиты только через `/commit`» (`~/.claude/CLAUDE.md` → «Git-коммиты»).

**Валидацию после вливания транка гнать заново** — объединённый код не собирал никто. Merge прошёл «чисто» ≠ код компилируется: транк мог поменять сигнатуру, которую ветка использует, без текстового конфликта. Покраснела → `❌ base merge broke validation`, Step 6 стоп, push не делать: гард «2.1 Validation не ❌» проверялся ДО вливания и этот случай не покрывает.

**Исключение — MR транк→транк** (релизный `develop → main`): обратное вливание `main` в `develop` запрещено git-флоу, шаг не применяется.

Почему шаг обязателен, а не «если push отклонят»: push отклоняется только при non-fast-forward, а MR с устаревшей базой пушится успешно и падает уже на стороне сервера — либо конфликтом (`detailed_merge_status: conflict`), либо, хуже, зелёным merge непроверенной комбинации. Прецедент 2026-08-20: MR создан, `has_conflicts: true` вскрылся только при попытке merge — за время задачи в транк влили два MR, и оба тронули тот же файл.

### Push

```bash
git push -u origin "$(git rev-parse --abbrev-ref HEAD)"   # апстрима нет
git push                                                   # апстрим уже есть
```

Push отклонён (non-fast-forward) → транк ушёл вперёд уже после шага выше: повторить обновление базы, прогнать билд заново, потом push. `--force-with-lease` допустим только на своей неслитой ветке; `--force` — нет.

### MR / PR

MR уже открыт (5.1a) — переиспользовать, не создавать второй.

```bash
# GitLab
glab mr create --fill --remove-source-branch --target-branch <trunk>
# GitHub
gh pr create --fill --base <trunk>
```

`--fill` берёт заголовок и тело из коммитов ветки. Есть активный документ задачи (`docs/active/...` или уже заархивированный) → дописать ссылку в тело (`glab mr update <iid> --description`, `gh pr edit <num> --body`). Документы задачи обязаны быть в этой же ветке — это проверяет 2.7b.

### Merge

```bash
# GitLab: squash + auto-merge (влить, когда pipeline станет зелёным)
glab mr merge <iid> --squash --auto-merge --remove-source-branch --yes

# GitHub: squash + auto-merge
gh pr merge <num> --squash --auto --delete-branch
```

Проверено 2026-08-10: glab 1.81.0, gh 2.88.1. `--when-pipeline-succeeds` в glab больше нет — GitLab 16.0 переименовал «merge when pipeline succeeds» в «auto-merge», флаг стал `--auto-merge`; при запущенном pipeline glab включает auto-merge по умолчанию, немедленный merge — `--auto-merge=false`. Стратегия по умолчанию — **squash**: одна задача = один коммит в транке, ревертится целиком.

Pipeline в проекте отсутствует → те же команды без `--auto-merge` / `--auto` (иначе gh уходит в ожидание проверок, которых не будет).

### Дождаться результата

```bash
glab mr view <iid>                                  # State: merged
gh pr view <num> --json state,mergedAt -q '.state'  # MERGED
```

Merge, поставленный в очередь по CI, **не** является «влито». Дождаться терминального состояния; ожидание длинное → сказать об этом и вернуть контроль, не заявляя завершение.

**Как ждать.** Нужно ОДНО уведомление «MR влит» — значит `Bash` с `run_in_background` и командой, которая сама завершится по достижении состояния. Это прямая рекомендация контракта `Monitor`: `Monitor` стримит поток событий и для одиночного ожидания не предназначен (у него нет «until-условия», он гоняет тот же скрипт опроса, который вы ему напишете).

Состояние читать **полем JSON**, а не грепом по человекочитаемому выводу — его формат не контракт:

```bash
# GitHub
until [ "$(gh pr view <num> --json state -q '.state')" = "MERGED" ]; do sleep 15; done

# GitLab
until [ "$(glab mr view <iid> -F json | jq -r .state)" = "merged" ]; do sleep 15; done
```

Запускать через `run_in_background: true` — тогда потолок таймаута foreground-вызова (дефолт 120 000 мс, максимум 600 000) не режет ожидание на второй минуте, а завершение придёт уведомлением. Ждёте в foreground — ограничьте цикл так, чтобы он укладывался в переданный `timeout`, и при исчерпании итераций верните контроль, как требует абзац выше, а не крутите дальше.

`sleep N; <проверка>` разовой парой — запрещено и блокируется хуком `bash-tool-discipline`: угадал мало — проверяешь ещё раз лишним вызовом, угадал много — простаиваешь. Внутри `until`/`while` и внутри `for` с `break` (ограниченный поллинг, как выше) короткая пауза законна — порог 30 с; голая пауза вне цикла судится порогом 10 с. Замер 2026-08-20…21: 23 таких пары за двое суток, все — ожидание CI на этом шаге.

## Отказы

| Ситуация | Действие |
|---|---|
| Красный pipeline | `❌ merge failed: pipeline red` + ссылка на job. Чинить причину. **Запрещено**: мержить в обход CI, `--admin`, отключать джобу, ретраить в надежде на flaky без разбора |
| Конфликт с транком | `git fetch origin && git rebase origin/<trunk>`, конфликты разрешить, билд прогнать заново, push. Не мержить транк в ветку, если в проекте линейная история |
| Валидация покраснела ПОСЛЕ вливания транка (шаг 0) | `❌ base merge broke validation` — Step 6 стоп, push не делать, отчёт пользователю с выводом сборки. Это не «flaky»: транк поменял то, на что опирается ветка, и починка идёт в ветке. Гард «2.1 Validation не ❌» этот случай не ловит — он проверялся ДО вливания |
| MR создан, а конфликт вскрылся только на merge | Шаг 0 был пропущен. Влить транк в ветку сейчас, прогнать валидацию, push в ту же ветку — MR обновится сам. Не разрешать конфликт в UI хостинга: там нет ни сборки, ни тестов |
| Нужен approval / protected branch rule | `⚠️ merge blocked: требуется approval` + ссылка на MR в блок `## 👉 Сделай руками`. Обходить правило approval нельзя |
| `gh` / `glab` не установлен или не авторизован | `gh auth status` / `glab auth status`. Не авторизован → MR не создавать вслепую: ссылка на веб-форму создания MR в блок ручных шагов |
| Remote — не GitHub и не GitLab | Ручной шаг: push сделан, ссылка на создание MR в UI |
| MR влит, но CI на транке покраснел после merge | Сообщить сразу, предложить revert (`git revert -m 1 <merge-sha>` либо revert squash-коммита) — не оставлять транк красным молча |

## Уборка (только после подтверждённого merge)

```bash
git push origin --delete <branch>   # если не сняли флагом --remove-source-branch / --delete-branch
```

Дальше — **выход из worktree тулом, а не `git worktree remove`**: сессия стоит внутри каталога, и снести его, не сменив CWD, нельзя (на Windows каталог просто залочен).

| Как заводили worktree | Уборка |
|---|---|
| `EnterWorktree({name})` в этой сессии | `ExitWorktree({action: "remove"})` — возвращает CWD, сносит каталог и локальную ветку |
| вошли по `EnterWorktree({path})` / worktree из прошлой сессии | `ExitWorktree({action: "keep"})`, затем из главного checkout `git worktree remove <путь>` и `git branch -d <branch>` (`-d`, не `-D`: проверяет, что ветка влита) |

`ExitWorktree` отказал с «commits not on the original branch» — после **squash**-merge это ожидаемо: squash кладёт в транк новый sha, коммитов ветки там буквально нет. Merge подтверждён (есть `Merged: <sha>`) → повторить с `discard_changes: true`. Merge не подтверждён → раздел «Отказы», ничего не сносить.

Отказ на незакоммиченных файлах → в worktree осталась несохранённая работа: `discard_changes` **не** ставить, показать `git status` пользователю. `git branch -d` отказывается → ветка не влита, merge не состоялся — раздел «Отказы».

```bash
git -C <main-checkout> checkout <trunk> && git -C <main-checkout> pull
```

### Каталог после `ExitWorktree` — проверять всегда

**Проверка идёт после КАЖДОГО `ExitWorktree({action: "remove"})`, в том числе когда он отчитался успехом,** и **не отменяется гардом профильного репозитория:** push, MR и merge для `~/.claude` / `~/.claude-work` пропускаются, уборка worktree — нет. Замер 2026-08-31 сделан именно там, и обе скорлупы накопились ровно потому, что уборка считалась частью пропускаемого шага.

Причина скорлуп — норма Windows, а не отказ: тул снимает регистрацию в git и выносит содержимое, но сам каталог удалить не может, пока его держит открытый хендл сессии, которая только что из него вышла. Ответ «could not remove it — kept at …» — явный признак; молчаливый успех его не исключает. Убрать такой каталог штатной командой уже нельзя: `git worktree list` его не показывает, `git worktree remove` отвечает `is not a working tree`, а в `.git/worktrees/` нет записи для этого пути (каталог `.git/worktrees/` при этом может быть непуст — там лежат записи ДРУГИХ живых worktree, и их наличие скорлупу не опровергает).

```bash
P="<путь>"                      # прямые слэши: обратный слэш в конце съест кавычку
if [ ! -d "$P" ]; then
    echo "ok: shell already gone"
elif [ -n "$(ls -A "$P")" ]; then
    echo "STOP: not a shell — files inside:"; ls -A "$P"
elif rmdir "$P"; then
    echo "ok: shell removed: $P"
else
    echo "WARN: rmdir refused (handle still open): $P"
fi
```

Ветвление, а не цепочка `&&`: однострочник молчит во всех исходах и возвращает одинаковый код на «каталога нет» и «каталог непустой» — то есть защитная ветка становится недостижимой, а отказ `rmdir` под `set -e` обрывает остаток шага, включая `git checkout <trunk>` выше.

Три исхода и что с ними делать:

| исход | что это значит | действие |
|---|---|---|
| каталога нет | тул справился сам | ничего, в отчёт `Cleanup: … removed` |
| каталог пуст → `rmdir` прошёл | скорлупа убрана | то же |
| каталог **непуст** | это не скорлупа, а недоснесённый worktree с файлами | **не трогать** (`rmdir` их и не удалит), показать `ls -A` пользователю и разобраться, что за работа осталась |
| `rmdir` отказал | хендл ещё держится | не ретраить, в отчёт `⚠️ worktree shell kept: <путь>` |

Замер 2026-08-31: в `.claude/worktrees/` лежали две пустые скорлупы от задач, влитых 19 и 31 августа. Копятся они молча и выглядят как незакрытая работа — на разбор одной ушёл отдельный заход со скаутом, и следов он не нашёл, потому что искал ветку и improvement-запись по имени каталога, а слаг записи был другим. Цена уборки — одна команда сразу, цена пропуска — археология через две недели.
