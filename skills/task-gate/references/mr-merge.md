# MR & Merge — Step 6

Extract из Step 6 `task-gate/SKILL.md`. Точные команды, гарды и обработка отказов для доведения задачи до **влитого** MR/PR.

## Принцип

Задача закрыта не коммитом и не открытым MR, а изменением в транке (`CLAUDE.md` → «Git-коммиты», «Защищённая ветка и worktree»). Пользователь подтверждает результат один раз — по отчёту gate; дальше вся цепочка push → MR → merge → уборка идёт без дополнительных вопросов. Спрашивать разрешение на каждый шаг — это возврат ручного режима, ради ухода от которого правило и вводилось.

## Разрешение

**Считается подтверждением:** «да», «готово», «подтверждаю», «мержи», «всё верно», «ок, вливай» — сказанные **после** отчёта gate, в ответ на строку `Подтверди результат — дальше сам: push → MR → merge…`.

**НЕ считается:** молчание; «спасибо»; переход к новой задаче; «посмотрю позже»; подтверждение, сказанное ДО прогона gate («да делай» в начале задачи); подтверждение отдельного шага («да, закоммить») — оно закрывает только этот шаг.

**Отзывается** любой репликой про недостаток («а вот тут поправь», «стоп», «не мержи»). Отозвано → Step 6 не запускается до нового подтверждения по новому отчёту gate.

### Без подтверждения: дифф только из документации

Дифф ветки против транка не меняет поведение ничего — подтверждение не нужно. Агент сам доводит задачу: gate (режим по 1.1; гейт обязателен и для docs-only задачи, хотя кода в ней нет) → коммит → Step 6 до влитого merge и уборки, не останавливаясь на отчёте. Дифф, прошедший условие, — это и есть команда на commit и push из `CLAUDE.md` → «Git-коммиты». Отчёт 5.2 печатается без строки `Подтверди результат…`, блок `🔀 Merge:` — с первой строкой `🔀 auto-merged: docs-only`. Merge сорвался (красный CI, нужен approval, конфликт) — раздел «Отказы», в отчёт `❌ merge failed`, повторно без пользователя не вливать.

**Условие — ВСЕ одновременно:**

1. Каждый файл из `git diff --name-only origin/<trunk>...HEAD` входит в класс документации:
   - `docs/**`;
   - `*.md` в корне репозитория (`README.md`, `CHANGELOG.md`, `CONTRIBUTING.md`);
   - в харнессе `~/.claude` дополнительно `improvements/**`.
2. Ни один файл не управляет агентами: `CLAUDE.md`, `AGENTS.md`, `GEMINI.md` на любом уровне, `.claude/**`, а в харнессе — `rules/`, `skills/`, `agents/`, `model-overlays/`, `output-styles/`, `commands/`, `hooks/`, `references/`, `settings*.json`. Для агента `.md` в этих местах — исполняемая инструкция, а не документация. Файл из `docs/**`, который `CLAUDE.md`/`AGENTS.md` импортирует через `@<путь>` или на который ссылается `rules/*.md`, — тоже инструкция: проверка `Grep` по имени файла в этих местах.
3. Ни один файл не попадает в сборку или витрину: `.md` внутри `src/`, `app/`, `public/`, `res/`, `assets/`, `content/` и подобных — контент продукта, класс не документация.
4. Merge в транк не запускает деплой (раздел «Деплой-предупреждение» ниже): сайт документации тоже выкатка. Сверх признаков 5.1a проверить деплой без CI-файла: GitHub — `gh api repos/{owner}/{repo}/pages` отдаёт `source.branch` = транк; в репозитории есть `mkdocs.yml`, `.readthedocs.yaml`, `docusaurus.config.*`, `book.toml`, `.gitbook.yaml`. Нашлось любое — условие не выполнено.
5. Гарды 1–5 выполнены, в отчёте gate нет `⚠️ diff review incomplete` и нет находок 2.3b, оставленных без фикса.

Не выполнено любое → обычный путь: отчёт и ожидание подтверждения. Правка комментариев в коде под исключение не идёт: дифф по файлу класса «код» не доказывает отсутствие влияния без ревью человеком. Явный запрет пользователя («пока не вливай», «MR сделаю сам») сильнее исключения.

## Гард-условия (ВСЕ одновременно)

| # | Условие | Проверка |
|---|---|---|
| 1 | Вердикт Step 5 — `READY` / `READY WITH WARNINGS`, ни одного `❌` | результат Step 5 |
| 2 | Ветка не защищённая | `git rev-parse --abbrev-ref HEAD` + реестр `~/.claude/config/protected-branches.local.json` |
| 3 | Рабочее дерево чистое | `git status --porcelain` пусто |
| 4 | Validation (2.1) не `❌` | билд/тесты не падали |
| 5 | Пользователь не запрещал merge в этой сессии | «MR сделаю сам», «пока не вливай» |
| 6 | Есть подтверждение либо дифф проходит исключение docs-only | см. выше |

Репозиторий харнесса `~/.claude` гардом не исключается: он публичный, правки в него идут через PR (скилл `harness-contributing`).

Не выполнено любое → Step 6 стоп, строка в отчёт с причиной. Гард 2 или 3 — это ещё и сигнал, что задача велась мимо worktree-правила; чинится до merge, а не после.

**Исключение из «Step 6 стоп» — уборка worktree (шаг 5).** Гарды останавливают push, MR и merge; каталог worktree убирается в любом случае, если сессия его заводила.

## Деплой-предупреждение

Merge в транк на проекте с CI-деплоем = выкатка пользователям. Признаки, которые проверяются в 5.1a:

- `.gitlab-ci.yml` — job с `only`/`rules` на транк и стадией deploy/publish;
- `.github/workflows/*.yml` — `on: push: branches: [<trunk>]`;
- `wrangler.jsonc` / `wrangler.toml` + Cloudflare Workers Builds на транке;
- Vercel/Netlify production branch = транк.

Нашлось → строка `⚠️ merge в <транк> запускает деплой <куда>` печатается **в отчёте gate**, до подтверждения. Пользователь подтверждает, уже зная это. Молча влить деплоящийся транк нельзя — это класс «деплой без сверки» из L3 process-gate.

Сверка аккаунта деплоя (`credentials-guard`, `~/.claude/config/project-credentials.local.md`) остаётся обязательной там, где деплой запускается локально; merge отдаёт выкатку CI, но расхождение аккаунта в CI-переменных агент не видит — если проект в реестре, назвать это в той же строке.

## Команды

Платформа определяется по `git remote get-url origin`: `gitlab` → glab, `github` → gh.

### Обновление базы (ПЕРЕД push, обязательный шаг)

Ветка ответвлялась от транка в НАЧАЛЕ задачи; к моменту MR транк почти всегда ушёл вперёд. Подтягивать его надо здесь, а не полагаться на то, что база свежая.

```bash
git fetch origin <trunk> || { echo "FETCH FAILED"; exit 1; }   # упавший fetch НЕ трактовать как «база свежая»
git merge-base --is-ancestor origin/<trunk> HEAD; case $? in
  0) echo UP-TO-DATE ;;
  1) echo BEHIND ;;
  *) echo "CHECK FAILED — битый ref, разбираться, а не пушить" ;;
esac
# BEHIND → влить транк в ветку и ПЕРЕПРОГНАТЬ валидацию (2.1) на объединённом коде
git merge origin/<trunk> --no-edit     # либо git rebase origin/<trunk> на неопубликованной ветке
```

`&& echo UP-TO-DATE || echo BEHIND` здесь не годится: `--is-ancestor` отдаёт 1 на «не предок» и >1 на ошибку, и однострочник отрапортует BEHIND на упавшем fetch — то есть на битом ref'е агент пойдёт «вливать транк», которого нет.

Конфликт — разрешать здесь, в своей ветке, где есть контекст задачи и можно прогнать сборку. Разрешение конфликта в UI GitLab/GitHub запрещено: там нет ни билда, ни тестов, а результат уезжает в транк непроверенным. Завершающий merge-коммит базы делается `git commit` напрямую — это единственное исключение из правила «коммиты только через `/commit`» (`~/.claude/CLAUDE.md` → «Git-коммиты»).

**Валидацию после вливания транка гнать заново** — объединённый код не собирал никто. Merge прошёл «чисто» ≠ код компилируется: транк мог поменять сигнатуру, которую ветка использует, без текстового конфликта. Покраснела → `❌ base merge broke validation`, Step 6 стоп, push не делать: гард «2.1 Validation не ❌» проверялся ДО вливания и этот случай не покрывает.

**Исключение — MR транк→транк** (релизный `develop → main`): обратное вливание `main` в `develop` запрещено git-флоу, шаг не применяется.

Почему шаг обязателен, а не «если push отклонят»: push отклоняется только при non-fast-forward, а MR с устаревшей базой пушится успешно и падает уже на стороне сервера — либо конфликтом (`detailed_merge_status: conflict`), либо, хуже, зелёным merge непроверенной комбинации. Прецедент 2026-08-20: MR создан, `has_conflicts: true` вскрылся только при попытке merge — за время задачи в транк влили два MR, и оба тронули тот же файл.

### Push

```bash
git push -u origin "$(git rev-parse --abbrev-ref HEAD)"   # апстрима нет
git push                                                   # апстрим уже есть
```

Push отклонён (non-fast-forward) → транк ушёл вперёд уже после шага выше: повторить обновление базы, прогнать билд заново, потом push. `--force-with-lease` допустим только на своей неслитой ветке; `--force` — нет.

### MR / PR

MR уже открыт (5.1a) — переиспользовать, не создавать второй.

```bash
# GitLab
glab mr create --fill --remove-source-branch --target-branch <trunk>
# GitHub
gh pr create --fill --base <trunk>
```

`--fill` берёт заголовок и тело из коммитов ветки. Есть активный документ задачи (`docs/active/...` или уже заархивированный) → дописать ссылку в тело (`glab mr update <iid> --description`, `gh pr edit <num> --body`). Документы задачи обязаны быть в этой же ветке — это проверяет 2.7b.

### Merge

```bash
# GitLab: squash + auto-merge (влить, когда pipeline станет зелёным)
glab mr merge <iid> --squash --auto-merge --remove-source-branch --yes

# GitHub: squash; --auto — только по условию ниже
gh pr merge <num> --squash --delete-branch
gh pr merge <num> --squash --auto --delete-branch   # есть обязательные проверки и включён auto-merge
```

**`--auto` на GitHub — по условию, а не всегда.** Auto-merge работает, только если он включён в настройках репозитория и у PR есть обязательные проверки, которые ещё идут. Иначе GitHub отвечает `GraphQL: Auto merge is not allowed for this repository (enablePullRequestAutoMerge)`, и PR остаётся `OPEN` (так было в логах сессий). Решение — по двум фактам:

```bash
gh api repos/{owner}/{repo} -q .allow_auto_merge            # true | false — включён ли auto-merge
gh pr checks <num> --required 2>&1 | grep -qiE "no (required )?checks reported" && echo NO_REQUIRED || echo HAS_REQUIRED
```

`gh repo view --json` поля auto-merge не отдаёт, поэтому — `gh api`. Код выхода `gh pr checks` здесь не годится: 8 — проверки ещё идут, 1 — упали или их нет вовсе; различает случаи только текст ответа: в репозитории без CI gh отвечает `no checks reported`, с CI без обязательных проверок — `no required checks reported` (первое проверено на gh 2.102.0, PR в репозитории харнесса). Сразу после `gh pr create` проверки может ещё не быть в списке: CI регистрирует их через несколько секунд. Поэтому `NO_REQUIRED` в первую минуту после создания PR — не факт: перепроверить через 30 с.

| `allow_auto_merge` | проверки | команда |
|---|---|---|
| `true` | `HAS_REQUIRED` | `--auto` |
| `false` | `HAS_REQUIRED` | дождаться зелёных проверок циклом из «Дождаться результата» по `gh pr checks <num> --required`, потом merge без `--auto` |
| любое | `NO_REQUIRED` | без `--auto` |
| пусто / `null` (нет прав admin на репозиторий) | `HAS_REQUIRED` | `--auto`; отказ `Auto merge is not allowed` → строка `false` |

Отказ `base branch policy prohibits the merge` на merge без `--auto` — gh печатает его на любой `BLOCKED`. Сначала причина: `gh pr view <num> --json reviewDecision,mergeStateStatus`. `reviewDecision` = `REVIEW_REQUIRED` или `CHANGES_REQUESTED` → строка «Нужен approval» раздела «Отказы», повторно не мержить. Иначе проверки появились позже — та же таблица заново.

**`--delete-branch` из worktree безопасен.** На gh 2.88 (2026-08-19) вызов из worktree падал на локальном шаге (`'main' is already used by worktree`), хотя merge на remote уже прошёл. На gh 2.102.0 в логах 80+ таких вызовов и ни одной этой ошибки. Ошибка вернулась → `gh pr view <num> --json state`: `MERGED` значит, что осталась только уборка, повторно не мержить.

Проверено 2026-08-10: glab 1.81.0, gh 2.88.1; поведение `--delete-branch` и `--auto` — 2026-11-16, gh 2.102.0. `--when-pipeline-succeeds` в glab больше нет — GitLab 16.0 переименовал «merge when pipeline succeeds» в «auto-merge», флаг стал `--auto-merge`; при запущенном pipeline glab включает auto-merge по умолчанию, немедленный merge — `--auto-merge=false`. Стратегия по умолчанию — **squash**: одна задача = один коммит в транке, ревертится целиком.

Pipeline в проекте отсутствует → те же команды без `--auto-merge` / `--auto` (иначе gh уходит в ожидание проверок, которых не будет).

### Дождаться результата

```bash
glab mr view <iid>                                  # State: merged
gh pr view <num> --json state,mergedAt -q '.state'  # MERGED
```

Merge, поставленный в очередь по CI, **не** является «влито». Дождаться терминального состояния; ожидание длинное → сказать об этом и вернуть контроль, не заявляя завершение.

**Как ждать.** Нужно ОДНО уведомление «MR влит» — значит `Bash` с `run_in_background` и командой, которая сама завершится по достижении состояния. Это прямая рекомендация контракта `Monitor`: `Monitor` стримит поток событий и для одиночного ожидания не предназначен (у него нет «until-условия», он гоняет тот же скрипт опроса, который вы ему напишете).

Состояние читать **полем JSON**, а не грепом по человекочитаемому выводу — его формат не контракт:

```bash
# GitHub
until [ "$(gh pr view <num> --json state -q '.state')" = "MERGED" ]; do sleep 15; done

# GitLab
until [ "$(glab mr view <iid> -F json | jq -r .state)" = "merged" ]; do sleep 15; done
```

Запускать через `run_in_background: true` — тогда потолок таймаута foreground-вызова (дефолт 120 000 мс, максимум 600 000) не режет ожидание на второй минуте, а завершение придёт уведомлением. Ждёте в foreground — ограничьте цикл так, чтобы он укладывался в переданный `timeout`, и при исчерпании итераций верните контроль, как требует абзац выше, а не крутите дальше.

`sleep N; <проверка>` разовой парой — запрещено и блокируется хуком `bash-tool-discipline`: угадал мало — проверяешь ещё раз лишним вызовом, угадал много — простаиваешь. Внутри `until`/`while` и внутри `for` с `break` (ограниченный поллинг, как выше) короткая пауза законна — порог 30 с; голая пауза вне цикла судится порогом 10 с. Замер 2026-08-20…21: 23 таких пары за двое суток, все — ожидание CI на этом шаге.

## Отказы

| Ситуация | Действие |
|---|---|
| Красный pipeline | `❌ merge failed: pipeline red` + ссылка на job. Чинить причину. **Запрещено**: мержить в обход CI, `--admin`, отключать джобу, ретраить в надежде на flaky без разбора |
| Конфликт с транком | Шаг 0: `git fetch origin <trunk> && git merge origin/<trunk>` в ветке, конфликты разрешить там же, валидацию прогнать заново, обычный push. Rebase — только на ещё не запушенной ветке: на опубликованной он требует force-push, а squash-merge и так схлопнет историю ветки в один коммит |
| Валидация покраснела ПОСЛЕ вливания транка (шаг 0) | `❌ base merge broke validation` — Step 6 стоп, push не делать, отчёт пользователю с выводом сборки. Это не «flaky»: транк поменял то, на что опирается ветка, и починка идёт в ветке. Гард «2.1 Validation не ❌» этот случай не ловит — он проверялся ДО вливания |
| MR создан, а конфликт вскрылся только на merge | Шаг 0 был пропущен. Влить транк в ветку сейчас, прогнать валидацию, push в ту же ветку — MR обновится сам. Не разрешать конфликт в UI хостинга: там нет ни сборки, ни тестов |
| Нужен approval / protected branch rule | `⚠️ merge blocked: требуется approval` + ссылка на MR в блок `## 👉 Сделай руками`. Обходить правило approval нельзя |
| `gh` / `glab` не установлен или не авторизован | `gh auth status` / `glab auth status`. Не авторизован → MR не создавать вслепую: ссылка на веб-форму создания MR в блок ручных шагов |
| Remote — не GitHub и не GitLab | Ручной шаг: push сделан, ссылка на создание MR в UI |
| MR влит, но CI на транке покраснел после merge | Сообщить сразу, предложить revert (`git revert -m 1 <merge-sha>` либо revert squash-коммита) — не оставлять транк красным молча |

## Уборка (только после подтверждённого merge)

```bash
git push origin --delete <branch>   # если не сняли флагом --remove-source-branch / --delete-branch
```

### 1. Освободить каталог — до `ExitWorktree`

Windows не удаляет каталог, пока он — текущий каталог живого процесса или в нём открыт файл. Поэтому перед выходом:

- `TaskStop` — каждая фоновая задача этой задачи (`run_in_background`: dev-server из 5.1b, watch-сборка, тест-раннер) и каждый `Monitor`;
- браузер Playwright закрыт (`browser_close`), запущенный тест-сервер остановлен;
- все субагенты вернулись: процесс субагента, который ещё работает, держит каталог.

Замер по логам сессий (2026-11-16, 210 сессий с `ExitWorktree remove`): каталог оставался в 68% сессий с dev-server против 38% без него, в 66% с Playwright против 38%, в 8 из 10 с `Monitor`.

### 2. Выйти тулом, а не `git worktree remove`

Сессия стоит внутри каталога, и снести его, не сменив CWD, нельзя.

| Как заводили worktree | Уборка |
|---|---|
| `EnterWorktree({name})` в этой сессии | merge подтверждён → сразу `ExitWorktree({action: "remove", discard_changes: true})` — возвращает CWD, сносит каталог и локальную ветку |
| вошли по `EnterWorktree({path})` / worktree из прошлой сессии | `ExitWorktree({action: "keep"})`, затем из главного checkout `git worktree remove <путь>` и `git branch -D <branch>` |

**`discard_changes: true` — сразу, а не повтором после отказа.** После squash-merge коммитов ветки в транке нет: squash кладёт туда новый sha. Поэтому вызов без флага всегда получает «Worktree has N commits…» (101 лишний вызов в логах). Проверку «влито ли» выполняет `MERGED` / `merged` из шага «Дождаться результата», а не отказ тула. Два условия флага, оба обязательны:

1. merge подтверждён (`MERGED` / `merged`);
2. `git status --porcelain` в worktree пуст. Флаг снимает и отказ на незакоммиченных файлах, поэтому правка после merge (например, по просьбе пользователя) иначе пропадёт молча.

Не выполнено первое → флаг не ставить, раздел «Отказы», ничего не сносить.

**`git branch -D`, а не `-d`.** После squash `-d` отказывает всегда («not fully merged») по той же причине и ничего не доказывает. Влитость подтверждает `MERGED`.

`git status --porcelain` непуст → в worktree осталась несохранённая работа: `discard_changes` **не** ставить, показать `git status` пользователю.

```bash
git -C <main-checkout> checkout <trunk> && git -C <main-checkout> pull
```

### 3. Каталог остался — работает хук, а не агент

**Уборка не отменяется никаким гардом:** даже когда push, MR и merge пропущены, worktree убирается.

На Windows `ExitWorktree` в половине сессий отвечает «could not remove it — kept at …» (105 из 210 по логам на 2026-11-16), иногда оставляет каталог молча. Git о нём уже не знает: `git worktree list` его не показывает, `git worktree remove` отвечает `is not a working tree`. Убирать его руками из сессии не нужно — каталог ловит PostToolUse-хук `hooks/worktree-exit-watch.ps1` (matcher `ExitWorktree`):

1. Запускает скрытый отложенный уборщик через WMI `Win32_Process.Create` — первым делом, чтобы долгий снимок не отменил его таймаутом хука. Уборщик вне job-объекта сессии и переживает её выход. Через 5 с, потом каждые 15 с, до 10 минут, пытается снести каталог по правилам `worktree-shell-sweep`: только каталог вне `git worktree list`; git не ответил — не трогать; непустой — только если `ExitWorktree` звали с `discard_changes: true` или локальной ветки нет; ветка жива — ждать дальше, пока агент её не удалит; `rmdir /s /q` не проходит внутрь junction. Итог — строка `event: cleanup` с `outcome: deleted | gone | gave_up | skipped_*` и `after_sec`; при `gave_up` — повторный снимок держателей.
2. Ищет держателей: процессы, у которых текущий каталог (читается из PEB), исполняемый файл или командная строка внутри каталога, и процессы с открытыми файлами (Restart Manager по файлам, оставшимся в каталоге: тул уже снёс всё незалоченное). У каждого — цепочка родителей до сессии Claude и пометка «запущен этой сессией». Если в PATH есть `handle64.exe` / `handle.exe` (Sysinternals), добавляет его вывод с таймаутом 5 с.
3. Пишет строку в `~/.claude/stats/worktree-holders.jsonl` (`event: exit`, `outcome: kept | kept_silent | removed`, держатели, `strong_holders` — найденные не только по командной строке, `files_left`, верхние записи каталога). Строка `removed` тоже пишется — по ней считается доля оставшихся каталогов.
4. Отдаёт агенту в контекст список держателей.

Что делает агент по сообщению хука:

| сообщение | действие |
|---|---|
| держатель с пометкой `started by this session` | остановить его (`TaskStop` фоновой задачи или `Monitor`, закрыть браузер Playwright, `gradlew --stop` для демона Gradle); дальше каталог снесёт уборщик |
| держатель без пометки (IDE, чужой dev-server, антивирус) | не убивать; в отчёт `Cleanup: worktree dir held by <name> — deferred cleanup` |
| держатель не найден | ничего: вероятно, короткий хендл самой сессии, уборщик снесёт каталог через 5–20 с |
| `Local branch … still exists` | merge подтверждён → `git -C <main-checkout> branch -D <branch>`; уборщик снесёт каталог на следующей попытке |

Ручной `rmdir`, блок «👉 Сделай руками» и повторный `ExitWorktree` под оставшийся каталог не нужны. Уборщик сдался (`gave_up`) — каталог снесёт SessionStart-хук `worktree-shell-sweep` при следующем старте в этом репозитории. В отчёт — строка `Cleanup: … deferred (worktree-exit-watch)`.

Диагностика по логу — какой держатель встречается чаще всего и сколько секунд проходит до удаления:

```bash
python -c "import json,collections,os;L=[json.loads(l) for l in open(os.path.expanduser('~/.claude/stats/worktree-holders.jsonl'),encoding='utf-8')];print(collections.Counter(l['outcome'] for l in L));print(collections.Counter(h['name'] for l in L for h in (l.get('holders') or [])).most_common(10))"
```
