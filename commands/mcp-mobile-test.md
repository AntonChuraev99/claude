# MCP Mobile Test — проверка на устройстве

Разделение труда: **Claude (подписка) думает, ARTEMIS (дешёвая Gemini-модель по API) кликает.** Качество прогона задаёт сценарий — исполнитель дешёвый и буквальный, поэтому в `task_desc` не оставлять ничего на догадку. Вердикт «прошло / не прошло» выносит Claude по скриншотам шагов и дереву UI, а не по самоотчёту ARTEMIS.

Установка и эксплуатация: `~/tools/artemis` (git clone `google/artemis`), ключ `GEMINI_API_KEY` в его `.env`, MCP `artemis` зарегистрирован в обоих профилях (`claude mcp get artemis`). Бесплатный тариф Gemini: запросы и скриншоты Google использует для обучения — риск принят пользователем 2026-09-30. Модель в `config/artemis.jsonc` локально переключена на `gemini-3.5-flash-lite` (fallback `3.1-flash-lite`): у дефолтной `gemini-3.8-flash` бесплатная квота 20 запросов в сутки на модель — 2-3 коротких сценария. Замер: сценарий из 3 шагов — 7 запросов, ~49k входных токенов. Квота flash-lite бесплатного тарифа не замерена — смотреть на aistudio.google.com/rate-limit в аккаунте ключа. `429 RESOURCE_EXHAUSTED` в логе ARTEMIS проявляется как `LLM call timed out after 180 seconds` — при таком таймауте первым делом проверять квоту, а не сеть.

## Аргументы

`$ARGUMENTS` — package, что проверять, уровень (`smoke` / `screen` / `flow` / `deeplink` / `full`). Пусто — `AskUserQuestion`.

## Phase 0: Готовность

1. `mcp__artemis__mobile_diagnose` — первым вызовом в сессии и после любой ошибки ARTEMIS. Идти дальше только при `verdict: ready|degraded`. `Run:`-строки выполнять самому. `Guidance:` с подсказкой следующего вызова (`probe_device=true`, `verify_credentials=true`, `attempt_fix=true`, `launch_avd`) — делать самому; в блок «Сделай руками» — только то, что требует человека (разблокировать телефон, разрешить USB-отладку, подключить кабель). Нет ключа — пользователь кладёт его в `.env` и перезапускает сессию; ключ через чат не передаётся.
2. Устройств несколько (`adb devices -l`) — выбор через `AskUserQuestion`, дальше всегда явный `device_serial`.
3. Свежая сборка — `/install-device` или `/install-emulator` до прогона (либо `app_path` в `mobile_run_task`).

## Phase 1: Сценарий — главная работа Claude

До запуска прочитать код экрана/фичи (тексты кнопок, testTag, ветки состояний) — исполнитель не знает приложения. `task_desc` собирать по шаблону:

```
Приложение: <package>. Стартовое состояние: <что открыто, залогинен ли, какие данные>.
Шаги:
1. <одно действие с точной подписью элемента: нажми кнопку «Создать» внизу справа>
   Проверка: на экране виден заголовок «Новый список».
2. ...
Если <ожидаемый элемент> не появился за 10 с — остановись и сообщи, что видно на экране. Не импровизируй обходных путей.
Завершение: после шага N сообщи статус и текст на экране.
```

Правила сценария:
- одно действие на шаг, подписи элементов дословно из строковых ресурсов;
- после каждого значимого шага — наблюдаемая проверка (текст, заголовок, наличие/отсутствие элемента);
- явное условие остановки на отклонении — дешёвая модель иначе «чинит» сценарий сама и маскирует баг;
- `locked_app_package` задавать всегда — агент не уходит в чужие приложения.

**Выбор модели:** `Flash` — линейный путь с известными подписями (дефолт). `Pro` + `verification_level: "checkpoints"` — ветвление, ожидания, нужен adb/logcat, или нужен письменный отчёт (`expected_output_desc`). `strict` — когда упавший assert должен останавливать прогон. `Flash`/`Pro` — профили исполнения, модель у обоих из конфига; `Pro` гоняет планировщик, исполнителя и проверяющего, на бесплатном тарифе это кратно больше запросов на шаг — брать только когда `Flash` не справится.

## Phase 2: Запуск и ожидание

1. `mcp__artemis__mobile_run_task` → вернёт `trace_id`, `stdout_log`, `stderr_log`.
2. Источник правды о статусе — `mcp__artemis__mobile_manage_task(action: "status", trace_id)`: только он сверяет `status.json` с базой трейсов и живостью процесса (сам файл может остаться `running` или `success` после конца прогона). Опрашивать не реже раза в минуту; паузу между опросами держать фоновым `Monitor` с until-циклом по `status.json` рядом со `stdout_log` (`completed|success|failed|cancelled`, `timeout_ms` ~60000) — срабатывание или истечение монитора = следующий опрос `status`. Число ходов растёт без прогресса → `inject_instruction` с подсказкой или `stop`.

## Phase 3: Вердикт — только по артефактам

1. `mcp__artemis__mobile_inspect_trace(action: "view_summary", trace_id)` — какие шаги сделаны.
2. Для каждой проверки из сценария — `view_step_screenshots` нужного шага, открыть кадр самому и сличить с ожидаемым. Самоотчёт «task completed» доказательством не является.
3. `failed` — читать `stderr_log` и `recent_errors` из `mobile_diagnose`, различать **баг приложения** (экран не тот, краш — `adb logcat -d` / `mcp__mobile__system(action: "logs")`) и **сбой исполнителя** (не нашёл элемент, ушёл не туда). Сбой исполнителя → уточнить сценарий и перезапустить, максимум 2 раза; дальше — `mobile` MCP вручную.
4. Финальное состояние перепроверить дешёво: `mcp__artemis__mobile_get_device_state(view_type: "hierarchy")`.

Повторяющийся сценарий (регресс) после первого успешного прогона превращать в детерминированный тест (Compose UI test / Maestro), а не гонять LLM каждый раз.

## Запасной путь — `mobile` MCP

Для точечной проверки одного экрана, строгих per-step assert'ов, deeplink'ов и когда ARTEMIS недоступен или дважды сорвался. Поверхность: `device`, `app`, `ui`, `screen`, `input`, `flow`, `system`.

- дерево UI — `ui(action: "tree", compact: true)`, дешевле скриншота в ~10 раз; скриншот — `screen(action: "capture", preset: "low")`;
- последовательность шагов — `flow(action: "batch")` / `flow(action: "run")`;
- deeplink — `system(action: "open_url", url)`; логи — `system(action: "logs")`;
- assert'ы — через `ui` (`action: "find"` / дерево), не через устаревшие плоские тулы.

Паттерны и типичные ошибки: `~/.claude/references/mcp-test-patterns.md` — **имена тулов там устаревшие** (`mcp__mobile__assert_visible`, `run_flow`, `analyze_screen`): брать оттуда приёмы, вызовы — только по поверхности выше.

```

Устройство: [serial] · Исполнитель: ARTEMIS Flash|Pro (trace_id) / mobile MCP · Уровень: …

### Проблемы
- [ ] Проблема — баг приложения | сбой исполнителя — кадр / лог
```
